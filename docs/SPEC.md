## 1. 概要

**Orange** (記号: **OAG**) は、RandomX を Proof of Work に用いる CPU マイニング型の
UTXO ブロックチェーンである。

| 項目 | 内容 |
| --- | --- |
| 合意形成 | Proof of Work (RandomX) |
| 会計モデル | UTXO |
| プライバシー | なし (透明台帳) |
| 署名 | Schnorr / BIP340 (secp256k1) |
| ブロック間隔 | 60 秒 |
| 総発行量 | 1,000,000,000 OAG |
| 初期配布 | **なし** (全量マイニングによって発行。ブロック 0 の報酬は焼却する) |
| 実装言語 | Rust |

### 設計目標

1. **公平な分配** — プレマイン・ICO・開発者報酬を一切持たない。RandomX の CPU 最適化
   により、専用ハードウェアを持たない参加者でも採掘に参加できる。
2. **単純さ** — スクリプト言語も仮想マシンも持たない。検証すべきものは署名と金額の
   帳尻のみ。攻撃面を最小に保つ。
3. **長期的な分配** — 半減期を持たない線形発行により、190 年にわたって新規参加者に
   採掘機会が残る。

### 明示的な非目標

- **プライバシー** — 本チェーンは透明台帳である。すべての取引額と取引の関連は
  公開され、チェーン分析が可能である。Monero 等のプライバシーコインではない。
- **スマートコントラクト** — 任意計算の実行環境を持たない。AMM 型 DEX、レンディング、
  デリバティブ等は本チェーン上では実現できない。
- **高スループット** — 約 17 tx/秒。決済ネットワークの置き換えを目的としない。

## 2. 表記と用語

- `u8`, `u32`, `u64`, `u128`, `i64` — 固定幅の符号なし / 符号付き整数。すべて
  リトルエンディアンでシリアライズする。
- `varint` — LEB128 可変長整数。7 ビットずつ格納し、最上位ビットが継続を示す。
- `atomic` — OAG の最小単位。1 OAG = 10^16 atomic。
- `[u8; N]` — 長さ N の固定長バイト列。
- **MUST / MUST NOT / SHOULD** — RFC 2119 に準ずる。

すべてのハッシュ値・鍵・署名は、16 進表記する際にビッグエンディアン
(バイト列の先頭が左) で記す。

### 個数フィールドの検査

列の先頭に置く個数の varint は、**その個数を符号化するのに足るバイト数が
残っていなければ拒否する MUST**。すなわち

```
個数 × (1 要素の最小符号化長) ≤ 残りバイト数
```

が成り立たないバイト列は不正である。

個数は相手が決める値でありながら、復号側はそれを見て領域を確保する。
「個数 ≤ 残りバイト数」とだけ比べる実装は、1 要素が実際には数十バイトを
要する型でも 1 バイト分の個数まで通してしまう。たとえば入力 1 個は最低 38
バイトを要するが、この緩い検査では 1 MiB のメッセージで入力 100 万個を
宣言でき、**1 件目の復号に失敗するより前に数十 MB を確保させられる**。
最小符号化長を掛けて比べれば、確保量は受け取ったバイト列と同じ桁に収まる。

主な型の最小符号化長 (バイト):

| 型 | 最小長 | 内訳 |
| --- | --- | --- |
| `OutPoint` | 33 | ハッシュ 32 + 出力番号 1 |
| `TxInput` | 38 | 参照 33 + 署名長 1 + sequence 4 |
| `TxOutput` | 3 | 金額 1 + lock 2 |
| `Transaction` | 7 | 版数 4 + 入力数 1 + 出力数 1 + locktime 1 |
| `BlockHeader` | 100 | 固定長 |

### 真偽値

真偽値は 1 バイトで表し、**`0x00` と `0x01` 以外は拒否する MUST**。
`!= 0` で受けると真を表すバイトが 255 通りになり、同じ値が複数のバイト列で
表現できる状態 — すなわち展性 — を作る。符号化側は常に `0x00` か `0x01` を
書くのだから、それ以外は壊れたバイト列である。

## 3. 通貨単位

```
1 OAG = 10,000,000,000,000,000 atomic   (10^16)
小数桁数 = 16
```

### 金額型

金額は **`u128`** で表現する。

```
総発行量 (atomic) = 1,000,000,000 × 10^16 = 10^25
u128 の最大値                             ≈ 3.40 × 10^38
```

`u64` (最大約 1.84 × 10^19) では表現できないため、`u128` を用いる。

### 実装上の必須要件

金額の算術は、コンセンサスに関わるすべての経路で以下を MUST とする。

1. **`Amount` を newtype で定義し、内部の `u128` を外部に露出しない。**

   ```rust
   pub struct Amount(u128);
   ```

2. **加算・減算・乗算はすべて `checked_*` を用いる。** オーバーフローが発生した場合、
   `None` を「無効なトランザクション」として扱う。

3. **`panic!` してはならない。** 攻撃者が任意のノードを停止できる DoS になる。
   オーバーフローは常に検証エラーとして扱う。

4. **すべての金額に範囲チェックを適用する。**

   ```
   0 ≤ amount ≤ MAX_SUPPLY  (= 10^25)
   ```

   この制約により、ブロック内の金額合計は数学的に `u128` を溢れない。
   200,000 バイトのブロックに入る出力数の上限は約 4,700 であり、
   `4,700 × 10^25 ≈ 4.7 × 10^28 ≪ 3.4 × 10^38` であるため。

5. **`Cargo.toml` の release プロファイルでも `overflow-checks = true` を有効にする。**
   静かに誤った金額を生成するより、異常終了する方が被害が小さい。

6. **RPC / JSON では金額を文字列として表現する MUST。**
   JavaScript の `Number` は 2^53 までしか正確に表現できず、
   atomic 単位の金額は容易にこれを超える。

> **背景**: Bitcoin は 2010 年 8 月、ブロック 74638 において整数オーバーフローにより
> 1,844 億 BTC を生成する事故を起こした (CVE-2010-5139)。出力金額の合計が `int64` を
> 溢れて負値に回り込み、「入力 ≥ 出力」の検証を通過したことが原因である。
> 本仕様の上記 1〜4 はこの事故の再発を構造的に防ぐためのものである。

## 4. 発行スケジュール

### パラメータ

```
BLOCK_REWARD          = 10 OAG = 10^17 atomic     (固定・不変)
MAX_SUPPLY            = 1,000,000,000 OAG = 10^25 atomic
EMISSION_END_HEIGHT   = 100,000,000
PREMINE               = 0
```

### 報酬関数

```
block_subsidy(height) =
    10 OAG   if height < 100,000,000
    0        otherwise
```

半減期は存在しない。報酬は発行終了高さまで一定である。

### 発行完了までの時間

```
100,000,000 ブロック × 60 秒 = 6,000,000,000 秒
                             ≈ 190 年 3 ヶ月
```

### 供給曲線

| 経過年 | 流通量 (OAG) | 総発行比 | 年間インフレ率 |
| ---: | ---: | ---: | ---: |
| 1 | 5,256,000 | 0.53 % | — |
| 2 | 10,512,000 | 1.05 % | 100.0 % |
| 3 | 15,768,000 | 1.58 % | 50.0 % |
| 5 | 26,280,000 | 2.63 % | 25.0 % |
| 10 | 52,560,000 | 5.26 % | 11.1 % |
| 20 | 105,120,000 | 10.51 % | 5.3 % |
| 50 | 262,800,000 | 26.28 % | 2.0 % |
| 100 | 525,600,000 | 52.56 % | 1.0 % |
| 190.3 | 1,000,000,000 | 100.00 % | 0 |

年間インフレ率は `1 / 経過年数` に従って減衰する (線形発行の数学的性質)。

### コインベーストランザクション

各ブロックはちょうど 1 個のコインベーストランザクションを含む MUST。

```
coinbase_output_total ≤ block_subsidy(height) + Σ(そのブロックの取引手数料)
```

不等号であることに注意。マイナーは報酬の一部または全部を放棄できる
(放棄された分は永久に発行されない)。

コインベース出力は **120 ブロック** が経過するまで使用できない
([コインベース成熟](#10-コンセンサスルール))。

## 5. 暗号プリミティブ

### 5.1 汎用ハッシュ関数: BLAKE3

トランザクション ID、マークルツリー、ブロックハッシュ、その他プロトコル内の
すべての汎用ハッシュには **BLAKE3** (256 ビット出力) を用いる。

```
H(x) = BLAKE3(x)[0..32]
```

BLAKE3 は長さ拡張攻撃に対して構造的に耐性があるため、Bitcoin のような
二重ハッシュ (`SHA256(SHA256(x))`) は不要である。

**ドメイン分離**: 用途ごとに異なるプレフィックスを付す。

```
txid          = H(0x00 || tx_serialized)
merkle_leaf   = H(0x01 || txid)
merkle_node   = H(0x02 || left || right)
block_hash    = H(0x03 || header_serialized)
```

用途が増える場面 (sighash など) では、1 バイトの識別子ではなく文字列タグを
用いる。[§8.0](#80-タグ付きハッシュ) を参照。

### 5.2 楕円曲線: secp256k1

```
p = 2^256 - 2^32 - 977
n = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141
G = (0x79BE667EF9DCBBAC55A06295CE870B07029BFCDB2DCE28D959F2815B16F81798,
     0x483ADA7726A3C4655DA4FBFC0E1108A8FD17B448A68554199C47D08FFB10D4B8)
```

秘密鍵 `d` は `1 ≤ d < n` を満たす MUST。

### 5.3 署名: Schnorr (BIP340)

**BIP340 に完全準拠する。**

- 公開鍵は **x-only 32 バイト**。Y 座標は偶数であるものと暗黙に定める。
- 署名は **64 バイト固定** (`r: 32 || s: 32`)。
- 内部のタグ付きハッシュは BIP340 の規定通り **SHA-256** を用いる
  (BLAKE3 ではない。これは BIP340 の仕様であり変更しない)。

  ```
  tagged_hash(tag, msg) = SHA256(SHA256(tag) || SHA256(tag) || msg)
  タグ: "BIP0340/challenge", "BIP0340/aux", "BIP0340/nonce"
  ```

- ノンス生成は BIP340 の補助乱数付き決定的方式に従う SHOULD。

**バッチ検証**: 実装は 1 ブロック内の全署名をバッチ検証する SHOULD。
個別検証比で約 2 倍高速であり、60 秒ブロック間隔において有意である。

**展性がないこと**: BIP340 署名は固定長かつ厳密な符号化を持ち、
本チェーンはスクリプトを持たない。したがって**第三者はトランザクション ID を
書き換えられない**。この性質により、SegWit 相当の機構を持たずとも
事前署名トランザクション (アトミックスワップの返金経路等) が安全に成立する。

> **0.4 までの例外 (0.5.0 で塞いだ)**: 署名欄は 64 バイト (既定形式) か
> 65 バイト (末尾が sighash 種別) である ([§8.3](#83-sighash-フラグ))。0.4 までは
> 65 バイトで末尾が `0x00` のものも既定形式として通していたため、**誰でも
> 64 バイトの署名の後ろに `0x00` を足すだけで、取引を有効なまま txid だけ
> 変えられた**。0.5.0 から、この形は中継しない ([§13.3.1](#1331-未知の版数の扱い-ポリシー層))。
> 合意の規則としても、[§10.9](#109-ソフトフォークの有効化-採掘者の印) の
> ソフトフォークが有効になったブロックから無効になる。上の性質が合意の上で
> 成り立つのは、そのソフトフォークが有効になってからである。

### 5.4 マークルツリー

**RFC 6962 (Certificate Transparency) 方式**を採用する。

```
MTH([])        = H(0x01 || 空)                      // 空ブロックは存在しないため未使用
MTH([d0])      = merkle_leaf(d0)
MTH(D[0..n])   = merkle_node(MTH(D[0..k]), MTH(D[k..n]))
                 ただし k は n 未満の最大の 2 冪
```

葉と内部ノードに異なるドメイン分離プレフィックスを用い、
奇数ノードの複製を行わない。

> **背景**: Bitcoin のマークルツリーは奇数ノードを複製して埋める設計のため、
> 異なるトランザクション列から同一のマークルルートを構成できる
> (CVE-2012-2459)。Bitcoin は「重複 txid の拒否」という後付けルールで
> 対処しているが、本仕様は構造的にこの問題を回避する。

さらにブロックヘッダは間接的にトランザクション数にコミットする
(コインベースの高さフィールドと合わせて検証される)。

## 6. 鍵とアドレス

### 6.1 アドレス形式

**bech32m (BIP350)** を用いる。SegWit v0 が bech32、v1 以降が bech32m という
Bitcoin の使い分けは歴史的経緯によるものであり、本チェーンは
**全バージョンで bech32m に統一する**。

```
<HRP> "1" <version> <payload(5bit変換)> <checksum(6文字)>
```

### 6.2 HRP (ネットワーク識別子)

| ネットワーク | HRP | 例 | 長さ |
| --- | --- | --- | ---: |
| mainnet | `oag` | `oag1q...` | 63 文字 |
| testnet | `toag` | `toag1q...` | 64 文字 |
| regtest | `roag` | `roag1q...` | 64 文字 |

HRP が一致しないアドレスはデコード時に拒否される MUST。
これによりネットワーク間の誤送金は構造的に発生しない。

### 6.3 アドレス版数

| version | 文字 | 内容 | 状態 |
| ---: | :---: | --- | --- |
| 0 | `q` | Schnorr x-only 公開鍵 (32 バイト) | v1 で実装 |
| 1 | `p` | 予約 (スクリプトハッシュ等) | 未定義 |
| 2 | | 予約 | 未定義 |
| 3 | | コミットメント出力 ([§7.7](#77-コミットメント出力))。**支払い先ではない** | 0.5.0 (ソフトフォーク) |
| 4–31 | | 予約 | 未定義 |

**未知の版数へは送金しない**: ウォレットは、意味を理解していない version の
アドレスへ送金してはならない MUST NOT。未知の版数の出力はソフトフォークで
有効になるまで誰でも使える ([§10.4](#104-未知の版数の扱い)) ため、送ると
資金を失う。新しい版数へ送れるようになるのは、ウォレットがその版数を
理解するように更新されてからである。

> 0.4 までの本書は「警告を表示した上で送金を許可する SHOULD」としていた。
> 有効化前の版数へ送れば誰でも取り出せるので、許可してはならなかった。
> 実装 (`oag-wallet`) は当初から送金を拒否しており、本書を実装に合わせた。

版数 3 は支払い先ではないので、**この版数のアドレスへ送金してはならない**。
コミットメント出力はウォレットの専用の操作で作る ([§7.7](#77-コミットメント出力))。

### 6.4 導出

```
秘密鍵 d  (32 バイト乱数, 1 ≤ d < n)
    │
    │  P = d × G
    ▼
公開鍵 P = (x, y)
    │
    │  BIP340: x のみを採用 (y は偶数を暗黙に選択)
    ▼
x-only 公開鍵 (32 バイト)
    │
    │  bech32m(HRP, version=0, payload)
    ▼
アドレス
```

ハッシュ関数は介在しない。公開鍵がそのままアドレスのペイロードとなる。

### 6.6 HD ウォレット

**BIP39 (ニーモニック) + BIP32 (導出) + BIP44 (経路)** に準拠する。

#### ニーモニック

```
語数         12 語
エントロピー  128 ビット
語彙         BIP39 英語 (2048 語)
検査符号      4 ビット
```

**12 語で足りる理由。** 128 ビットは secp256k1 が実際に持つ強度と一致する。
256 ビットの曲線に対する最良の一般攻撃 (Pollard の rho) の計算量は 2^128 で
あり、24 語 (256 ビット) の種を用いても、そこから導かれる鍵を守る強度は
2^128 のままである。**種を長くしても曲線より強くはならない。** 頭打ちの
ところで長くしても、書き写しの誤りが増えるだけである。

#### 追加パスフレーズ (BIP39 の任意項目)

対応する。既定は空文字列とする。

**打ち間違えても失敗として現れない。** 別のパスフレーズは単に別の有効な
ウォレットを作る。利用者から見えるのは残高 0 のウォレットだけで、
どこにも誤りは表示されない。ウォレットはこの性質を設定時に明示する MUST。

#### 導出経路

```
m / 44' / <coin_type>' / <account>' / <change> / <index>

change = 0  受取用
change = 1  お釣り用
ギャップリミット = 20
```

| ネットワーク | coin_type | 状態 |
| --- | ---: | --- |
| testnet | 1 | SLIP-0044 が全コインのテストネット用に予約済み。登録不要 |
| regtest | 1 | 同上 |
| mainnet | 1033 | SLIP-0044 へ申請済み・**審査待ち** (下記) |

**1033 はまだ確定していない。** `satoshilabs/slips` が別の番号で受理した
場合、この値を書き換えることになり、**同じ控えから導かれる mainnet の鍵は
すべて変わる**。利用者から見れば、それは資金が消えたのと区別がつかない。

したがって運用上の境目はこうである。

- ウォレットは mainnet の鍵を導出してよい。経路は
  `m/44'/1033'/0'/0/<index>` で固定する
- 番号が確定するまで、mainnet のアドレスへ資金を入れない、というのが
  当初の決まりだった。**実際には、mainnet は登録の確定を待たずに
  2026-09-17 に動き出し、資金も入っている** (§19)
- 番号が変わった場合に捨てるのは導出経路であって控えではない。控えの語は
  そのまま使え、新しい経路から出るアドレスへ移す。したがって別の番号で
  受理されたら、**ウォレットは古い経路 (1033) の鍵も読み続け、新しい経路の
  アドレスへ移す手段を用意しなければならない MUST**

#### SLIP-0044 への登録

`satoshilabs/slips` リポジトリの `slip-0044.md` が唯一の登録簿である。

1. **先に BIP44 対応のウォレットを実装する。** 登録簿は「そのコイン向けに
   BIP-0044 を実装したウォレットが存在する場合にのみコインタイプを追加する」
   と定めている。実装が申請の前提であり、順序を逆にはできない。**これは
   実装済みである。**
2. 使われていない番号を 1 つ選ぶ。番号は連番ではなく、大きな空きがある。
3. `slip-0044.md` の表に 1 行を加えるプルリクエストを `satoshilabs/slips`
   へ出す。表は `Coin type | Symbol | Coin` の 3 列である。
   **提出済み: `satoshilabs/slips` のプルリクエスト #2062。審査待ち。**
   (先に 1031 で出した #2061 は、同じ番号の先着があったため閉じた)

申請した番号は **1033** である。1032 と 1042 の間の空きであり、`OAG` も
`Orange` も登録されていない。

```text
| 1032       | BTCR    | BTCR                              |
| 1033       | OAG     | Orange                            |   ← 加える行
| 1042       | MFID    | Moonfish ID                       |
```

**番号を選ぶときは、登録簿の本体だけでなく審査待ちのプルリクエストも見る
こと。** 登録簿に空いていても、先に申請している者がいれば衝突する。当初は
1031 (登録簿で最も小さい空き) で申請したが、6 日前に提出されていた
プルリクエスト #2059 が同じ 1031 を NYEN 用に要求していたため、1033 へ
改めた。1031 と 1033 のあいだの 1032 は BTCR が使用中である。

**この番号はまだ確定していない。** 実装は
`crates/oag-wallet/src/seed.rs` の `COIN_TYPE_MAINNET` に 1033 を置き、
`coin_type(Network::Mainnet)` がこれを返す。取り込まれれば、この定数は
そのままでよい。別の番号で受理された場合は、この定数 1 つを書き換えると
**それまでに mainnet で作られたアドレスの鍵が導けなくなる**。mainnet の
公開を登録の完了まで待つつもりだったのはこのためで、待たずに公開した
今は、上のとおり古い経路も読めるように残す。

正式な申請様式も審査基準も文書化されていない。**採否も所要期間も保証が
ないため、これを mainnet 公開の工程に組み込む。** testnet は番号 1 を使い、
この登録に一切依存しない。

secp256k1 を採用したことにより、BIP32 の**非強化導出**が利用できる。
これは拡張公開鍵 (xpub) のみから子アドレスを無限に生成できることを意味し、
サーバに秘密鍵を一切置かずに顧客ごとの入金アドレスを発行する運用が可能である。
(Ed25519 系ではこの運用は原理的に不可能である。)

### 6.7 アドレス再利用に関する注意

本チェーンは透明台帳である。同一アドレスを再利用すると、そのアドレスに紐づく
すべての取引履歴と残高が第三者から完全に閲覧可能となり、一度でも身元が
紐づけられれば過去・未来の全取引が特定される。

ウォレットは受取のたびに新しいアドレスを生成する MUST。

## 7. トランザクション

### 7.1 構造

```
Transaction {
    version:       u32
    input_count:   varint
    inputs:        TxInput[input_count]
    output_count:  varint
    outputs:       TxOutput[output_count]
    locktime:      varint          // u64 として解釈
}

TxInput {
    prev_txid:     [u8; 32]
    prev_index:    varint
    sig_len:       varint          // 64 または 65
    signature:     [u8; sig_len]
    sequence:      u32
}

TxOutput {
    amount:        varint          // u128 (atomic 単位)
    version:       u8              // アドレス版数
    payload_len:   varint          // 2〜40
    payload:       [u8; payload_len]
}
```

#### 出力が自己記述的であること

`payload_len` は省略できない。長さが版数から暗黙に決まる設計では、**未知の版数の
出力に遭遇したノードがそこで読み進められなくなる**。その結果、[§6.3](#63-アドレス版数)
と [§17.3](#173-将来の拡張余地) で確保した拡張枠を使うたびにハードフォークが
必要になってしまう。

長さを明示することで、版数 1 以降を追加してもすべての旧ノードが出力を読み飛ばせる
(意味を解さないため標準外として中継はしないが、ブロックの構造は読める)。
Bitcoin の出力が `scriptPubKey` に明示的な長さを持つのと同じ理由である。

コストは出力あたり 1 バイトである。

### 7.2 標準トランザクションのサイズ

本仕様における **基準トランザクション** を、1 入力 2 出力・金額が 9 バイトの
varint に収まる送金と定める。容量と手数料の見積もりはこれを単位とする。

```
入力  1 個:  prev_txid 32 + prev_index 1 + sig_len 1 + 署名 64 + sequence 4
                                                          = 102 バイト
出力  2 個:  (金額 9 + version 1 + payload_len 1 + payload 32) × 2
                                                          =  86 バイト
その他:      version 4 + 入力数 1 + 出力数 1 + locktime 1  =   7 バイト
──────────────────────────────────────────────────────
合計                                                      = 195 バイト
```

入力に公開鍵を含めない点に注意。使用対象の UTXO が既に公開鍵を保持している。

| 指標 | 値 |
| --- | ---: |
| 基準トランザクション | **195 バイト** |
| 200,000 バイトブロックあたりの件数 | 約 1,025 件 |
| スループット | 約 17.1 件/秒 |

#### 金額の符号化長は額に依存する

小数 16 桁を採用した結果、金額の varint 長は額によって変わる。

| 金額 | atomic 値 | varint 長 |
| ---: | ---: | ---: |
| 0.001 OAG | 10^13 | 7 バイト |
| 1 OAG | 10^16 | 8 バイト |
| **7.2058 OAG** | **2^56** | **8 → 9 バイトの境界** |
| 10 OAG | 10^17 | 9 バイト |
| 100 OAG | 10^18 | 9 バイト |
| 1,000 OAG | 10^19 | 10 バイト |

したがって同じ 1 入力 2 出力でも、少額送金 (7.21 OAG 未満) は **193 バイト**、
基準トランザクションは **195 バイト**、高額送金 (721 OAG 以上) は **197 バイト**
となる。見積もりには基準トランザクションを用いる。

これは小数桁数を 16 とした選択の直接の帰結である。8 桁であれば金額は
4〜5 バイトで済んだ。

### 7.3 手数料の表現

手数料は明示的なフィールドを持たない。

```
手数料 = Σ(入力が参照する UTXO の金額) − Σ(出力の金額)
```

この差額はコインベースを通じてマイナーが回収する。
**お釣りの出力を書き忘れると、差額の全額が手数料となる。**
ウォレットはこれを検出して警告する MUST。

### 7.4 locktime

```
locktime < 500,000,000   → ブロック高さとして解釈
locktime ≥ 500,000,000   → Unix 秒として解釈
locktime = 0             → 制約なし
```

時刻として解釈する場合、比較対象は直前ブロックの
**Median Time Past** (直近 11 ブロックのタイムスタンプの中央値) である。

条件は以下である。`locktime` は「このトランザクションを含められる最も早い
時点」を意味する。

```
高さとして解釈する場合:  ブロック高さ ≥ locktime
時刻として解釈する場合:  Median Time Past ≥ locktime
```

> **Bitcoin との差異**: Bitcoin は `locktime < 高さ` を条件とするため、
> `locktime = 100` のトランザクションが有効になるのは高さ 101 からである。
> この 1 つずれた意味論は混乱の元であり、本チェーンは採用しない。
> `locktime = 100` はちょうど高さ 100 から有効になる。

`locktime` は `u64` として保持する。`u32` では 2106 年に破綻するため。

### 7.5 sequence (相対 locktime)

BIP68 に準ずる意味論を定める。

```
tx.version < 2  → 相対 locktime は無い (sequence の値によらない)
bit 31 = 1      → 相対 locktime を無効化
bit 31 = 0      → 相対 locktime を有効化
    bit 22 = 0  → bits 0-15 をブロック数として解釈
    bit 22 = 1  → bits 0-15 を 512 秒単位として解釈
その他のビット   → 意味を持たない (将来のために空けておく)
```

数え始めは**参照先の出力が入ったブロック**である。条件は §7.4 と同じく
1 つずれない形で書く。

```
ブロック数:  ブロック高さ      ≥ 出力の高さ + 値
時間:        Median Time Past ≥ MTP(出力の高さ) + 値 × 512
```

`MTP(h)` は高さ `h` のブロックを検証したときの Median Time Past、すなわち
高さ `h − 1` までの直近 11 ブロックのタイムスタンプの中央値である。
高さ 0 には親が無いので下限を置かない。左辺の Median Time Past は、
§7.4 と同じく検証しているブロックのものである。

BIP68 と同じ結果になる。BIP68 は「最小値 − 1 < 現在」と書くが、整数では
「最小値 ≤ 現在」と同じである。値 0 は常に満たす。同じブロックの前の
トランザクションが作った出力は、そのブロックの高さで生まれたものとして
数えるので、値 0 なら同じブロックで使え、1 以上なら使えない。

#### 強制は版数 2 以上に限る

版数 1 のトランザクションは、`sequence` に意味が無かった時期に作られた。
**後から意味を与えて、それらを無効にしてはならない。** BIP68 と同じ線引き
である。標準のウォレットは版数 1 と `sequence = 0xFFFFFFFF` で作るので、
強制の影響を受けない。

#### 強制の開始 (ソフトフォーク)

v1 は相対 locktime を強制しなかった。強制は**以下の高さ以降のブロック**で
始まる MUST。それより前のブロックは強制なしで検証する MUST。

| ネットワーク | 強制を始める高さ |
| --- | ---: |
| mainnet | 40,000 |
| testnet | 0 |
| regtest | 0 |

**ソフトフォークである。** 条件を厳しくするだけなので、更新したノードが
作るブロックは、更新していないノードにとっても有効なままである。逆に、
更新していない採掘者は条件を満たさないトランザクションを含むブロックを
作りうる。そのブロックは更新したノードに捨てられる。採掘者の大半が開始の
高さまでに更新を終えている必要がある。

mainnet の高さは、強制を入れた版の公開から約 2 週間後に置いた (高さ
21,190 の時点で 1 日あたり約 1,450 ブロック)。testnet と regtest は最初から
強制する。どちらも版数 2 のトランザクションを作る道具が無いうちに始めて
いるので、過去のブロックが無効になることはない。

#### mempool は高さによらず確かめる

ノードは、開始の高さより前でも、相対 locktime を満たさないトランザクション
を mempool に入れない SHOULD。開始の前はポリシーであり、後はコンセンサス
である。開始の瞬間に、抱えていたものでブロックを作って自分で弾かれる
ことが起きない。

mempool の中の出力は、次のブロックの高さで生まれたものとして数える。
したがって、未確認の親を待つ値 1 以上の子は mempool に入らない。

#### 何に使うか

相対 locktime は、「この出力が承認されてから一定期間」を事前署名した
トランザクションで表す。出力がいつ承認されるかを署名の時点で知らなくて
よいことが、絶対 locktime との違いである。

- 双方向の支払いチャネル (取り消した古い状態を出されたとき、相手が
  反応するための猶予を作る。スクリプトを持たない本チェーンでは、
  アダプター署名と組み合わせて構成する)
- アトミックスワップの返金 ([§17.2](#172-アダプター署名によるアトミックスワップ))
- 一定期間動きが無ければ別の鍵へ移せる相続・金庫の仕組み

**`sequence` は置き換え可能の表明には使わない MUST。** BIP125 の規則 1 に
あたる用法であり、本チェーンは採らない ([§13.3.2](#1332-手数料を上げた置き換え-rbf))。
この 1 つのフィールドに相対 locktime と置き換えの可否という無関係な 2 つの
意味を載せると、片方を設定したつもりでもう片方が変わる。

### 7.6 コインベーストランザクション

ブロックの最初のトランザクションはコインベースである MUST。

```
CoinbaseTransaction {
    version:       u32
    input_count:   varint = 1
    input: {
        prev_txid:  [u8; 32] = すべて 0
        prev_index: varint   = 0xFFFFFFFF
        sig_len:    varint   // 追加ノンス用の任意データ長 (最大 100)
        signature:  [u8; sig_len]   // 先頭に height を varint で含む MUST
        sequence:   u32
    }
    output_count:  varint
    outputs:       TxOutput[]
    locktime:      varint = 0
}
```

`signature` フィールドは署名ではなく、マイナーの追加ノンス領域として使う。
先頭にブロック高さを含めることで、異なる高さのコインベースが
同一 txid を持つことを防ぐ (Bitcoin BIP34 と同趣旨)。

### 7.7 コミットメント出力

**金額 0 で、2〜40 バイトの中身を刻むだけの、誰にも使えない出力**である。
ハッシュの記録 (タイムスタンプ、リリースの証明、鍵の引き継ぎの宣言など) に
用いる。スクリプトやデータの置き場ではない。Bitcoin の `OP_RETURN` 出力に
あたる。

```
TxOutput {
    amount:      0
    version:     3
    payload_len: 2..=40
    payload:     刻む中身
}
```

[§10.9](#109-ソフトフォークの有効化-採掘者の印) のソフトフォークが有効に
なったブロックから、次の規則を課す MUST。

1. 版数 3 の出力は、金額が 0 でなければ**無効**である。コインベースの出力も
   含む。
2. 版数 3 の出力は **UTXO セットに入れない**。したがって誰にも使えない。
   同じブロックの後のトランザクションからも見えない。
3. 巻き戻し情報の「作った出力」にも載せない。巻き戻しはそれに触らないので、
   **巻き戻し情報の形は変わらない**。

中身の長さ (2〜40) は従来の出力の規則 ([§7.1](#71-構造)) のままである。
合意は中身を解釈しない。名前空間や意味づけはすべてアプリケーションの側に
置く。

**有効化より前に作られた版数 3 の出力は、さかのぼって扱いを変えない。**
それらは UTXO に残っており、未知の版数として誰でも使えるまま
([§10.4](#104-未知の版数の扱い)) である。規則が効くのは、規則の効いている
ブロックで作られた出力だけである。

中継の側の扱い ([§13.3.1](#1331-未知の版数の扱い-ポリシー層)):

| | 有効化の前 | 有効化の後 |
| --- | --- | --- |
| 版数 3 の出力を作る | 中継しない (未知の版数) | 中継する。ほこりの判定から外す |
| 1 トランザクションに入れる数 | — | **1 個まで** (合意の規則ではない) |
| 版数 3 の出力を使う | 中継しない | 中継しない |

住所の索引 ([§15.4](#154-エクスプローラ)) にも載せない。エクスプローラと
RPC は、この出力をアドレスに変換せず `commitment: 16 進` と表示する。

## 8. 署名対象 (Sighash)

**BIP341 方式**を採用する。

本チェーンはスクリプトを持たないため、BIP341 の `scriptPubKey` に相当するのは
出力の**支払い条件** (`version || payload_len || payload`。以下 lock と呼ぶ) である。

### 8.0 タグ付きハッシュ

```
tagged(tag, msg) = BLAKE3(tag のバイト列 || 0x00 || msg)
```

BIP340 は `SHA256(SHA256(tag) || SHA256(tag) || msg)` という構成を用いるが、
これは SHA-256 が長さ拡張攻撃を受けることへの対処である。BLAKE3 は構造的に
長さ拡張耐性を持つため、タグと NUL 区切りの前置で足りる。タグに NUL を
含めないため、この符号化は前置符号となり、異なるタグが同じ入力列を
生じることはない。

### 8.1 構成

```
msg =
    0x00                                       // エポック
    hash_type                          u8      // §8.3 のバイト
    tx.version                         u32 LE
    tx.locktime                        u64 LE

    ─── ANYONECANPAY でない場合のみ ───────────────────────
    tagged("OAG/sighash/prevouts",   全入力の prev_txid || prev_index)
    tagged("OAG/sighash/amounts",    全入力が参照する UTXO の金額)      ★
    tagged("OAG/sighash/locks",      全入力が参照する UTXO の lock)      ★
    tagged("OAG/sighash/sequences",  全入力の sequence)

    ─── 出力へのコミット (基本種別による) ─────────────────
    ALL / DEFAULT : tagged("OAG/sighash/outputs", 出力数 || 全出力)
    SINGLE        : tagged("OAG/sighash/outputs", 1 || 対応する出力)
    NONE          : (何も含めない)

    input_index                        u32 LE

    ─── ANYONECANPAY の場合のみ ───────────────────────────
    この入力の prev_txid || prev_index
    この入力が参照する UTXO の金額                                      ★
    この入力が参照する UTXO の lock                                     ★
    この入力の sequence                u32 LE

sighash = tagged("OAG/sighash", msg)
```

★ を付した 3 項目が [§8.2](#82-全入力金額へのコミット) の対象である。

`SINGLE` において対応する出力が存在しない場合、署名は生成できない。
Bitcoin の「ハッシュ値 1 を返す」という挙動は採用せず、明確な誤りとする。

#### 中間ハッシュは入力番号に依存しない

上の構成のうち、`H(prevouts)`、`H(amounts)`、`H(locks)`、`H(sequences)`、
および `ALL` における `H(outputs)` の 5 つは、**入力番号の関数ではない**。
同じトランザクションのどの入力についても同じ値になる。

実装はこれを 1 トランザクションにつき 1 度だけ計算するべきである
(SHOULD)。入力ごとに組み立て直すと、入力 n 個のトランザクションで同じ
ものを n 回ハッシュすることになり、**計算量が O(n²) になる**。入力 1 個が
これらのバッファに足す量はおよそ 76 バイトなので、`MAX_TX_SIZE` いっぱい
の約 980 入力では 73 MB をハッシュすることになる。

**これは最適化であって規則ではない。** どちらで計算しても sighash の値は
同じであり、コンセンサスには影響しない。

### 8.2 全入力金額へのコミット

`H(すべての入力が参照する UTXO の金額)` を含めることが本仕様の重要点である。

> **背景**: Bitcoin の初期の sighash は入力金額にコミットしていなかった。
> このため、悪意ある PC がハードウェアウォレットに偽の入力金額を伝えて署名させ、
> 差額を全額マイナー手数料として流出させる攻撃が成立した。
> Bitcoin は BIP143 (SegWit) でこれを修正した。
> 本仕様は初版からこれを含め、ハードウェアウォレットが単独で手数料を
> 検算できるようにする。

### 8.3 Sighash フラグ

| 値 | 名称 | 意味 |
| ---: | --- | --- |
| `0x00` | DEFAULT | `ALL` と同義。署名は 64 バイト (フラグバイトを省略) |
| `0x01` | ALL | 全入力・全出力にコミット |
| `0x02` | NONE | 出力にコミットしない |
| `0x03` | SINGLE | 同じインデックスの出力のみにコミット |
| `0x81` | ALL \| ANYONECANPAY | 自分の入力のみ + 全出力 |
| `0x82` | NONE \| ANYONECANPAY | 自分の入力のみ |
| `0x83` | SINGLE \| ANYONECANPAY | 自分の入力 + 対応する出力のみ |

`0x00` 以外の場合、署名は 65 バイトとなり最終バイトがフラグとなる。

**`0x00` を 65 バイトで書いてはならない。** 既定形式は 64 バイトで書く。
65 バイトで末尾が `0x00` の署名は、中継しない MUST。
[§10.9](#109-ソフトフォークの有効化-採掘者の印) のソフトフォークが有効に
なったブロックでは、**無効**である MUST (Bitcoin の BIP341 と同じ)。
これを許すと、第三者が署名の後ろに `0x00` を足すだけで txid を変えられる
([§5.3](#53-署名-schnorr-bip340))。

上表に無いバイト (`0x04` 以降、および `ANYONECANPAY` 単独の `0x80`) は
**未定義であり拒否する MUST**。

`SINGLE | ANYONECANPAY` は部分署名トランザクションの構築に用いる。
[相互運用性と DEX](#17-相互運用性と-dex) を参照。

## 9. ブロック

### 9.1 ブロックヘッダ (100 バイト固定)

```
BlockHeader {
    version:       u32        //  4  offset  0
    prev_hash:     [u8; 32]   // 32  offset  4
    merkle_root:   [u8; 32]   // 32  offset 36
    timestamp:     i64        //  8  offset 68   Unix 秒
    difficulty:    u64        //  8  offset 76
    height:        u64        //  8  offset 84
    nonce:         u64        //  8  offset 92
}                             // 合計 100 バイト
```

`nonce` を末尾に配置することで、マイナーは末尾 8 バイトのみを書き換えて
反復できる。

### 9.2 タイムスタンプが i64 である理由

Bitcoin のブロックヘッダは `u32` のタイムスタンプを持ち、
**2106 年 2 月 7 日にオーバーフローする**。

本チェーンの発行完了は 2026 年から約 190 年後、すなわち **2216 年**であり、
確実にこの時点を跨ぐ。したがって `u32` は採用できない。

### 9.3 難易度の表現

Bitcoin の `nBits` (4 バイト圧縮形式) は採用しない。難易度を `u64` で直接保持し、
ターゲットは以下で導出する。

```
MAX_TARGET = 2^256 − 1
target(difficulty) = MAX_TARGET / difficulty      (整数除算)
```

`nBits` は非正準な符号化や符号ビットの扱いに起因するバグを歴史的に生んでおり、
また LWMA は難易度を直接扱うため、`u64` の方が単純かつ安全である。

### 9.4 ブロック

```
Block {
    header:       BlockHeader
    tx_count:     varint
    transactions: Transaction[tx_count]
}
```

### 9.5 aux_pow (マージマイニング) の予約

`version` フィールドの **bit 0** を `AUX_POW` フラグとして予約する。

```
version & 0x00000001 == 0  → RandomX(header) を直接検証   (v1 の唯一の経路)
version & 0x00000001 == 1  → 親チェーンの PoW を検証       (未定義)
```

v1 においてこのビットが立ったブロックは**無効**とする。
将来 Monero とのマージマイニングを導入する際、
補助 PoW のデータはヘッダ外 (ブロック本体) に配置し、
ヘッダのサイズと構造は変更しない。

`version` の他のビットは、ソフトフォークの印に使う
([§10.9](#109-ソフトフォークの有効化-採掘者の印))。合意は bit 0 以外を見ないので、
印を付けたブロックは旧ノードにも有効である。

## 10. コンセンサスルール

### 10.1 パラメータ

```
TARGET_BLOCK_TIME        = 60 秒
MAX_BLOCK_SIZE           = 200,000 バイト
MAX_TX_SIZE              = 100,000 バイト
COINBASE_MATURITY        = 120 ブロック  (2 時間)
MEDIAN_TIME_SPAN         = 11 ブロック
MAX_FUTURE_TIME_DRIFT    = 300 秒
```

`MAX_FUTURE_TIME_DRIFT` は Bitcoin の 2 時間より大幅に短い。
60 秒ブロックにおいて 2 時間は 120 ブロック分の裁量を与えることになり、
難易度操作の余地が大きすぎるため。

`COINBASE_MATURITY` は **Bitcoin の 100 ブロックより深い**。実時間では
2 時間と短く見えるが、比べる単位はブロック数である。リオーグを押し返すのに
要るのは累積作業量であり、それはブロック数に比例する
(→ [§19 の決着した項目](#決着した項目))。

### 10.2 ブロックの検証

ブロックは以下をすべて満たす MUST。

1. シリアライズサイズが `MAX_BLOCK_SIZE` 以下
2. `header.height == 親ブロックの height + 1`
3. `header.prev_hash` が既知の有効なブロックを指す
4. `header.timestamp > 親ブロックの Median Time Past`
5. `header.timestamp ≤ ノードの現在時刻 + MAX_FUTURE_TIME_DRIFT`
6. `header.difficulty` が [LWMA](#12-難易度調整-lwma) の計算結果と一致する
7. `header.version` の `AUX_POW` ビットが 0
8. PoW が有効 ([Proof of Work](#11-proof-of-work))
9. `header.merkle_root` がトランザクション列から再計算した値と一致する
10. 最初のトランザクションがコインベースであり、それ以外はコインベースでない
11. コインベースの `signature` 先頭の高さが `header.height` と一致する
12. すべてのトランザクションが有効
13. コインベース出力の合計 ≤ `block_subsidy(height) + 手数料合計`
14. 同一ブロック内で同一 UTXO を二重に使用していない
15. ブロックが空でない
16. コインベースに 1 個以上の出力があり、`MAX_TX_SIZE` を超えない

### 10.3 トランザクションの検証

1. 入力が 1 個以上、出力が 1 個以上ある
2. シリアライズサイズが `MAX_TX_SIZE` 以下
3. すべての入力が、UTXO セットに存在する未使用の出力を参照する
4. コインベース出力を参照する場合、`現在の高さ − 生成高さ ≥ COINBASE_MATURITY`
5. すべての出力金額が `0 ≤ amount ≤ MAX_SUPPLY`
6. `Σ入力 ≥ Σ出力` (checked 演算で評価。オーバーフロー時は無効)
7. すべての入力について、参照先の支払い条件を[§10.4](#104-未知の版数の扱い)に従って検査する
8. すべての入力の署名が [BIP340](#53-署名-schnorr-bip340) 検証を通過する
9. `locktime` の条件を満たしている
10. 同一トランザクション内で同一 UTXO を二重に使用していない
11. 強制を始める高さ以降のブロックでは、すべての入力の相対 locktime の
    条件を満たしている ([§7.5](#75-sequence-相対-locktime))

### 10.4 未知の版数の扱い

出力の版数がノードにとって未知である場合、**コンセンサス上は誰でも使用できる
(anyone-can-spend) ものとして扱い、署名を検査しない MUST**。

#### なぜ拒否してはならないか

未知の版数を無効としてしまうと、新しい版数を導入するたびに旧ノードが
新しいブロックを拒否することになり、**版数の追加が必ずハードフォークになる**。
それでは出力に長さ接頭辞を設けた意味 ([§7.1](#71-構造)) が失われる。

anyone-can-spend としておけば、後から**ソフトフォークで条件を厳しくする**ことで
版数を有効化できる。旧ノードから見れば「誰でも使えるはずの出力を、新ノードが
より厳しく検査している」だけであり、新ノードが作るブロックは旧ノードにとっても
有効なままである。Bitcoin が SegWit の導入に用いたのと同じ機構である。

#### 伴う危険

**版数が有効化されるまでの間、その版数のアドレスへ送金してはならない。**
誰でも取り出せる資金になる。以下で緩和する。

| 層 | 対策 |
| --- | --- |
| ウォレット | 未知の版数のアドレスへは送金しない ([§6.3](#63-アドレス版数)) |
| ノードポリシー | 未知の版数を含む出力を作るトランザクションを中継しない |
| ノードポリシー | 未知の版数の出力を使用するトランザクションを中継しない |

ポリシー層の 2 つはコンセンサスルールではないため、マイナーが直接ブロックに
含めることは妨げられない。これは Bitcoin と同じ性質である。

#### 決定 (確認済み)

この扱いを**維持する**。

より安全に見える代替は「未知の版数は無効」である。しかしそれを選ぶと、
版数を追加するたびに旧ノードが新ブロックを拒否する。**版数の追加が必ず
ハードフォークになる**のであり、出力を自己記述的にした意味
([§7.1](#71-構造)) がそこで失われる。小規模なネットワークにとって、
全ノードの同時更新を要求するハードフォークは、上表の 3 層ですでに
緩和されている資金喪失より危険である。

そのうえで、**版数の範囲だけを狭める**。

```
出力の version が 32 以上のトランザクションは無効とする MUST
```

アドレスの版数は bech32m の 5 ビット領域に載るため 0〜31 しか表現できない
([§6.3](#63-アドレス版数))。32 以上の版数は**いかなるアドレスからも到達
できない**。アドレスを経由しない出力形式を将来加えるとしても、空いている
1〜31 の 31 枠で足りる。したがってこの制限はソフトフォークの余地を減らさず、
anyone-can-spend として扱う面積だけを 255 種類から 31 種類へ減らす。

この制限は**すでに効いている**。`Lock` は版数 32 以上を構築時にも復号時にも
断るため、32 以上の版数を含むトランザクションはそもそも読めない。

### 10.5 検証順序 (DoS 対策)

RandomX の light モード検証は 1 ハッシュあたり数ミリ秒を要する。
攻撃者が無効なヘッダを大量送信することでノードの CPU を枯渇させられるため、
**PoW の検証は最後に行う MUST**。

```
① 親ブロックが既知か                (ハッシュマップ参照)
② height が親 + 1 か               (整数比較)
③ timestamp が範囲内か             (整数比較)
④ difficulty が期待値と一致するか    (整数比較)
⑤ version の AUX_POW ビットが 0 か  (ビット演算)
   ────── ここまで通過したもののみ ──────
⑥ RandomX 検証                    (数ミリ秒)
```

加えて、ピアごとにヘッダ受信のレート制限を適用する MUST。

#### 接続とヘッダの守り (0.5.0)

外から繋ぐだけでノードを止められないよう、次を課す。値は実装の既定である。

| 項目 | 値 | 内容 |
| --- | --- | --- |
| ハンドシェイクの時間切れ | 60 秒 | 名乗り合いが済むまでの上限。済むまでは `ping` が動かないため |
| ハンドシェイク中のペイロード上限 | 1 KiB | `version` / `verack` しか来ないので、1 MiB を溜めさせない |
| 受け入れる接続の上限 | 117 本 | Bitcoin Core の 125 本から外向きの 8 本を引いた数 |
| 同じ IP から受け入れる接続の上限 | 4 本 | ループバックは数えない |
| ヘッダ受信のレート制限 | 4,000 件まで溜め、毎秒 1,000 件戻る | ピアごと。PoW を確かめる前に見る |
| 出入り禁止 | 24 時間 | 不正なヘッダ (PoW・難易度・時刻・無効な祖先) か、レート制限を超えた相手。メモリにだけ持つ |

`accept` が失敗しても (ファイル記述子を使い切ったときなど)、待ち受けは
止めずに続ける MUST。0.4 までは止まり、再起動するまで受け入れなかった。

不正なブロックの本体を送ってきた相手は、切るだけで出入りを禁じない。
ソフトフォークの前後で、更新していないノードが新しい規則に反するブロックを
運ぶことがあるためである。

#### 軽い枝は記憶域に書かない

ヘッダ 1 つに要る作業量はその高さの難易度で決まる。**難易度の低かった昔の
高さから分岐させれば、正しいヘッダを安く大量に作れる**ので、検証を通った
ものを全部書くと、それでディスクを埋められる。

そこで、**最良のヘッダの累積作業量から 144 ブロック分 (最良のヘッダの
難易度 × 144) を引いた値**より軽い枝のヘッダは、記憶域に書かずに手元
(メモリ、最大 50,000 件) に置く MUST。続きが届いて閾値を超えたら、その
ときに祖先ごと書く。軽い枝のブロック本体も書かない (ヘッダだけ手元に
置く)。Bitcoin Core の anti-DoS の閾値と同じ考え方である。

**これはリオーグの深さの上限ではない** ([§10.6](#106-最長チェーンの選択))。
どれほど深く分岐した枝でも、最良のヘッダに迫るほど作業量を積めば書かれ、
切り替わる。手元に置いたヘッダの続きは、最後に受け取ったヘッダを起点に
`getheaders` で求める。

**PoW を確かめるのは、ヘッダをインデックスに載せるときの 1 度だけである
(0.1.2 から)。** 本体を繋ぐときには確かめ直さない。ヘッダはハッシュで本体と
結び付いているので、本体が届いてもヘッダは変わらない。

0.1.1 までは、本体を繋ぐときにも確かめ直していた。1 度の切り替えで繋ぐ
ブロックはシードのエポック ([§11.3](#113-シードエポック)) をまたぐことがあるのに、
検証器は引き金になったブロックのエポックのものしか用意していなかった。
他のエポックのブロックは PoW が必ず合わず、正しいブロックに無効の印が
付いた。印は永続化され子孫へ広がるので、初期同期中のノードが正しい
チェーンへ戻れなくなった。0.1.2 のノードは、起動のたびに無効の印を外して
見直す。本当に無効なブロックは、繋ぎ直そうとした時点でまた印が付く。

### 10.6 最長チェーンの選択

累積作業量 (各ブロックの `difficulty` の総和) が最大のチェーンを採用する。
ブロック数ではなく作業量で比較する。

**同点の扱い**: 累積作業量が等しい先端が複数あるときは、**ブロックハッシュが
小さいほうを選ぶ** MUST。ただし現在の先端と同点の場合は現在の先端を保つ
(先に受け取ったチェーンを優先する)。同点の順序を決めておかないと、同じ
作業量のチェーンが 2 本届いたときにノードごとに違う先端を選び、合意が割れる。

先端の候補は**本体を持つブロックに限る**。ヘッダだけ知っているブロックは
接続できないため候補にならない ([§14.5](#145-p2p-プロトコル))。
候補の祖先をたどってアクティブチェーンに合流するまでの経路が、すべて本体を
持っていることも確かめる MUST。

再編成 (リオーグ) の深さに上限は設けない。**設けてはならない MUST。**
上限より深く分かれたネットワークは二度と合流しない
(→ [§19 の決着した項目](#決着した項目))。

これは**規則としての上限**の話である。手元に巻き戻し情報を残していない
ために戻れないノードは、規則が上限を設けたのとは違う。**その場合も
別の状態に落ち着いてはならない MUST NOT。** 追従できないことを告げ、
運用者が引き直せるようにする (→ [§19](#決着した項目))。

#### 分岐した 2 台が揃うまで

離れている間に別々のブロックを掘った 2 台は、繋がった時点で異なる帳簿を
持っている。揃うまでの道筋は次のとおりである。

```
        分岐点
          │
   A ─────┼── a1 ── a2 ── a3                作業量 3
          └── b1 ── b2 ── b3 ── b4 ── b5    作業量 5   B
```

1. 繋がる。`version` で互いの高さを知る
2. 遅れている側 (A) が `getheaders` を送る。ロケータには A 自身の枝が
   並ぶ。B はそのどれも知らないので、**両者が最後に一致する高さ**
   — ここでは分岐点 — の次から `b1..b5` のヘッダを返す
3. A はヘッダを検証してインデックスに載せる。この時点で先端は動かない。
   本体が無いものは繋げないからである ([§14.5](#145-p2p-プロトコル))
4. A は `b1..b5` の本体を古い順に取り寄せる
5. `b5` が届いた時点で B の枝の作業量が A の先端を上回る。A は
   `a3, a2, a1` を取り消して UTXO セットを巻き戻し、`b1..b5` を
   **自分で検証しながら**繋ぎ直す

作業量が同点の間は切り替えない。したがって同じ高さで分かれた 2 台は、
繋がっただけでは揃わない。**どちらかが次の 1 つを掘った時点で揃う。**

取り消した枝のコインベースは UTXO セットから消える MUST。残すと、
存在しない金が使えることになる。コインベース成熟
([§7.6](#76-コインベーストランザクション)) は、この取り消しが起きうる
期間に報酬が流通するのを防ぐためにある。

#### 取り消された枝のトランザクション

リオーグは UTXO セットだけの話ではない。**mempool もアクティブチェーンの
先を写したものであり、先端が動けば合わせ直す必要がある。**

取り消された枝に入っていたトランザクションは、また未確認に戻る。

- 取り消された枝の非コインベースを **mempool へ戻す SHOULD**。戻さないと、
  一度は確認まで進んだ支払いがどのノードの mempool にも無いまま消える。
  送った側が送り直すまで、二度と掘られない
- **コインベースは戻さない MUST。** 取り消された枝のコインベースはもう
  存在しない報酬である
- 戻す前に、**リオーグ後の UTXO で検証し直す MUST**。新しい枝が同じ UTXO を
  使っていれば二重使用になる

新しい枝で確認済みになったものは mempool から外す MUST。残したまま採掘
すると、そのトランザクションを詰めたブロックは入力が無く、**自分で掘った
ブロックが自分で弾かれる**。

#### 残ったものも検証し直す

外すのは「取り消された枝のもの」と「新しい枝に入ったもの」だけでは足り
ない。**リオーグは、残っているトランザクションの前提も崩す。**

| 崩れるもの | 起きること |
| --- | --- |
| 親が取り消された枝にあり、戻せなかった | 使おうとしている出力が存在しない |
| 高さが戻った | コインベース成熟 ([§7.6](#76-コインベーストランザクション)) に届かなくなる |
| 高さが戻った | locktime が再び未来になる |

したがって、リオーグの後は **mempool 全体をリオーグ後の UTXO で検証し直す
SHOULD**。落ちたものを選んで外すのでは、上の 3 つを取りこぼす。

費用は mempool の大きさに比例する (署名の検証をやり直す)。リオーグは稀で
あり、mempool には上限があるので、選別の複雑さ
より全件の検証を取る。

本実装では `Mempool::rebuild_after_reorg` がこれを行う。戻すものと残って
いるものを合わせ、**親を子より先に並べ替えてから**順に受け入れ直す。子を
先に出すと、その時点では親の出力が無く落ちてしまう。

#### 負けた枝に入っただけのものは外さない

受け取ったブロックがアクティブチェーンに入らなかった場合 (サイドチェーン)、
**mempool を触ってはならない MUST NOT。** そのブロックに入っている
トランザクションは依然として未確認であり、こちらの先端から見れば有効な
ままである。ここで外すと、まだ有効な支払いを中継しなくなり、自分が掘る
ときにも詰めなくなる。分岐はごく普通に起こるので、影響は小さくない。

#### 実装上の要請: 候補の探索を全件走査にしない

先端の候補を「ブロックインデックス全体を走査して作業量最大のものを探す」と
実装すると、ブロック 1 個あたり O(n)、初期同期の全体では O(n²) になる。
本実装は作業量順の集合を漸進的に保ち、末尾から現先端を上回る分だけを見る
(Bitcoin の `setBlockIndexCandidates` に相当)。

実測 (候補探しだけを切り出し、1 ブロックあたり):

| ブロック数 | 全件走査 | 漸進的な索引 |
| ---: | ---: | ---: |
| 1,000 | 1.8 μs | 0.037 μs |
| 10,000 | 31.5 μs | 0.051 μs |
| 100,000 | 655 μs | 0.062 μs |
| 400,000 | 7,070 μs | 0.072 μs |

同じ条件で、記憶域への書き込みは 1 ブロックあたり約 1,500 μs である。
数千ブロックの段階では全件走査の費用は書き込みに埋もれて見えない。
**10 万ブロック (約 2 か月半) で書き込みに匹敵し、そこから先は支配的になる。**

最も作業量の多いヘッダ ([§14.5](#145-p2p-プロトコル)) と、無効の印を
子孫へ広げる操作についても同様に、全件走査を避ける。

### 10.7 受け取り側の確認数

**これはコンセンサスルールではない。** ノードが拒む基準ではなく、資金を
受け取る側が「もう覆らない」と判断する目安である。

チェーンの側に確定を宣言する仕組みは無い。リオーグの深さに上限を設けない
([§10.6](#106-最長チェーンの選択)) 以上、どの承認数であっても覆る確率は
0 にならない。決めるのは受け取り側である。

| 場面 | 確認数 | 実時間の目安 | 種別 |
| --- | ---: | ---: | --- |
| 支払いとして受け取る | **10** | 約 10 分 | 目安 |
| 高額 / 引き渡すと取り戻せないもの | 20 以上 | 約 20 分以上 | 目安 |
| コインベース (採掘報酬) | 120 | 約 2 時間 | **コンセンサスルール** ([§7.6](#76-コインベーストランザクション)) |
| ゼロ承認 | **受け取ってはならない MUST** | — | [§13.3.2](#1332-手数料を上げた置き換え-rbf) |

#### 10 とした根拠

比べる単位は**時間ではなくブロック数**である。ハッシュレート比 q を持つ
攻撃者が z 承認を追い抜く確率は q と z だけで決まり、**ブロック間隔には
依存しない** (Bitcoin whitepaper §11)。したがって「1 ブロックが 60 秒
だから Bitcoin の 10 倍待つ」という換算は誤りである。

| q (攻撃者の占有率) | z = 6 | z = 10 | z = 20 | z = 120 |
| ---: | ---: | ---: | ---: | ---: |
| 10 % | 0.024 % | 0.00012 % | ~0 | ~0 |
| 20 % | 1.43 % | 0.11 % | 0.0002 % | ~0 |
| 25 % | 4.99 % | 0.85 % | 0.011 % | ~0 |
| 30 % | 13.2 % | 4.17 % | 0.25 % | ~0 |
| 35 % | 28.2 % | 14.3 % | 2.77 % | 0.0000004 % |
| 40 % | 50.4 % | 36.0 % | 16.4 % | 0.010 % |

Bitcoin の慣習は 6 である。本チェーンは **10** を目安とする。同じ q に
対して、覆る確率は 6 承認のおよそ 1 桁下になる。

6 で足りない理由は確率ではなく**費用**である。q は「全体の何割を持つか」
であり、その割を買う値段はネットワーク全体のハッシュレートに比例する。
**若いチェーンでは全体が小さいので、同じ q が安く買える。** 確率の式は
この差を映さない。映らない分を承認数で少し埋める。

待ち時間は 10 分である。1 ブロックが 60 秒なので、Bitcoin の 6 承認
(約 60 分) より短い。**確率で上、待ち時間で下**という位置になる。

#### 10 を超えて待つべき場合

- 引き渡すものが取り戻せない (現物、デジタル財、他チェーンへの出金)
- 受け取る額が、10 ブロック分の報酬 (100 OAG + 手数料) と比べて大きい。
  攻撃者が捨てる報酬より儲けが大きければ、攻撃は割に合う
- 直前にハッシュレートが大きく落ちている。難易度が追いつく
  ([§12](#12-難易度調整-lwma)) までの間は、同じ承認数が安く覆る

#### リオーグが起きたとき

**確認数は増えるだけではない。減るし、消える。**

分岐が解消されると、負けた枝に入っていた支払いは未確認に戻る
([§10.6](#106-最長チェーンの選択))。受け取る側から見ると次のようになる。

| リオーグ後 | 起きること |
| --- | --- |
| 新しい枝にも同じ支払いが入っている | 確認数が**その分だけ戻る** (9 → 2 など)。いずれまた伸びる |
| 新しい枝にまだ入っていない | 確認数が **0 に戻る**。mempool へ戻され、また掘られるのを待つ |
| 新しい枝が同じ UTXO を別の宛先へ使った | **その支払いは二度と確認されない。** 二重使用が成立した形である |

3 つめが、承認を待つ理由そのものである。9 承認で品物を渡し、10 ブロックの
リオーグが起きれば、渡したものは戻らない。

ウォレットは**毎回チェーンの UTXO セットを見直す**ため、リオーグの後に
`balance` を実行すれば正しい値が出る。前回の表示を覚えていて食い違う、
ということは起こらない。ただし**減ったことを知らせる仕組みは無い**。
一度 10 承認を見たからといって、その後に見直さなくてよいわけではない。

したがって、承認数は**渡す直前に確かめる**こと。10 承認を見てから品物を
用意する間に戻っているかもしれない。

#### 実装での扱い

`oag-consensus::params::RECOMMENDED_CONFIRMATIONS` に 10 を置く。
ウォレットの `balance --verbose` は UTXO ごとの確認数を表示し、10 に
満たないものに印を付ける。**印は表示だけであり、送金は妨げない。** 何を
待つかは受け取り側が決めることであって、ウォレットが決めることではない。

### 10.8 assumevalid (初期同期の短縮)

初期同期では、創世記から先端までの**すべての署名を検証し直す**。高さが
伸びるほどここが同期時間の大半になる。

十分に深く埋まったブロックについては、手元で検証し直さないという選択が
ありうる。攻撃者はそこまで遡って PoW を積み直せないためである。

**これはコンセンサスルールではない。** 受け入れるブロックの集合は変わら
ない。設定の異なるノード同士が同じチェーンに収束する。したがって実装は
これを持たなくてよく、既定では無効でよい。

#### 規則

実装がこれを持つ場合、署名の検証を省いてよいのは次を**すべて**満たす
ブロックに限る。

1. 利用者または実装が**あらかじめ指定したブロック** A が存在する。
2. 検証対象のブロック B が、**A と一致するか A の祖先である**。

B が A の祖先であることは、A から親を辿って高さ B に達したハッシュが
B と一致することで確かめる。

#### 省いてよいのは署名の検証だけである

次はすべて従来どおり検証する。

- PoW、難易度、タイムスタンプ、高さ、親への参照
- マークルルート
- ブロックとトランザクションのサイズ
- 金額の帳尻、コインベースの受け取り額
- 二重使用 (ブロック内、UTXO 集合の双方)
- コインベースの成熟期間、locktime
- 署名欄の長さ、sighash 種別、公開鍵と署名の形式

**楕円曲線上の検証 1 回だけを省く。**

#### なぜ祖先であることを要求するか

要求しないと、攻撃者が「高さ h 以下の別のチェーン」を食わせるだけで
署名検査を止められる。祖先であることを要求すれば、攻撃者のチェーンは
指定ブロックの祖先にならないので、何も省かれない。指定ブロックそのものを
偽造するには BLAKE3 の原像を求める必要がある。

指定したブロックをまだ受け取っていない間は、**何も省かない**。

#### 何を信じることになるか

**指定したブロックが本物のチェーン上にあること。** これは検証ではなく
**仮定**である。誰かの言を信じている。

したがって、

- 実装は**利用者がこれを無効にできるようにしなければならない** (MUST)。
- ネットワークごとの既定値を置く場合、**そのハッシュと高さを公表し**、
  利用者が独立に確かめられるようにしなければならない (MUST)。
- 起動時に**効いていることを告げなければならない** (MUST)。黙って検証を
  やめてはならない。

#### 実装での扱い

`oag-node` は `--assumevalid <hash>` で受け取り、`--assumevalid=0` で
無効にする。ネットワークごとの既定値は現在どれも空である (`None`)。
値を置くには、その高さのブロックが本物であると主張できるだけの時間が
必要であり、まだ経っていない。

mempool は**常に完全検証**である。これは深く埋まった過去にだけ許される
緩和であり、未確認トランザクションには適用されない。

### 10.9 ソフトフォークの有効化 (採掘者の印)

0.5.0 から、ソフトフォークは**採掘者がブロックに印を付け、十分な数に
届いてから有効にする**。Bitcoin の BIP9 に倣う。違いは、期間を時刻ではなく
高さで区切ることだけである (BIP8 と同じ)。

#### 印

ヘッダの `version` の上位 3 ビットが `001` (`0x20000000`) で、かつ割り当てた
ビットが立っているブロックを「印が付いている」とする。bit 0 は AUX_POW に
予約済み ([§9.5](#95-aux_pow-マージマイニング-の予約)) なので使わない。
合意は bit 0 以外を見ないので、印付きのブロックは旧ノードにも有効である。

#### 状態

```
  Defined ──(開始の高さ)──▶ Started ──(閾値に届く)──▶ LockedIn ──▶ Active
                              │
                              └──(期限の高さ)──▶ Failed
```

- 状態は**区切り (period) の頭でしか変わらない**。区切りの頭の高さは
  period の倍数である。高さ 0 で始まる区切りは `Defined`。
- 区切り `P` の状態は、区切り `P − period` の状態と、その区切り
  (高さ `P − period` から `P − 1`) で印の付いたブロックの数で決まる。
  - `Defined`: `P ≥ 期限` なら `Failed`、`P ≥ 開始` なら `Started`。
  - `Started`: 印が閾値以上なら `LockedIn`。そうでなく `P ≥ 期限` なら
    `Failed`。**閾値を期限より先に見る** (Bitcoin Core と同じ)。
  - `LockedIn` の次は必ず `Active`。猶予の区切りで印が減っても取り消さない。
  - `Active` と `Failed` は以後変わらない。
- 状態は**祖先のブロックのヘッダだけ**から決まる。本体は要らない。
  リオーグで枝が変われば、答えも枝に従って変わる。実装は区切りの最後の
  ブロックのハッシュに紐付けて覚えてよい。
- 採掘者は `Started` と `LockedIn` の間、印を付ける。

#### 0.5.0 のソフトフォーク (commitments)

コミットメント出力 ([§7.7](#77-コミットメント出力)) と、65 バイトで末尾が
`0x00` の署名を無効にする規則 ([§8.3](#83-sighash-フラグ)) を、1 つの印で
まとめて有効にする。

| ネットワーク | ビット | 区切り | 閾値 | 数え始め | 期限 |
| --- | ---: | ---: | ---: | ---: | ---: |
| mainnet | 1 | 1,440 (約 1 日) | 960 (2/3) | 40,320 | 565,920 (約 1 年後) |
| testnet | — | — | — | 最初から有効 | — |
| regtest | — | — | — | 最初から有効 | — |

数え始めは、相対 locktime の強制 (高さ 40,000、[§7.5](#75-sequence-相対-locktime))
より後の最初の区切りの頭である。ソフトフォークは続けて重ねない。

有効になったブロック (`Active` の区切りに属するブロック) から規則を課す。
それより前のブロックは規則なしで検証する MUST。

ノードの `getinfo` は `softfork` に状態と、いまの区切りで印の付いた数を返す。

## 11. Proof of Work

### 11.1 アルゴリズム

**RandomX** ([tevador/RandomX](https://github.com/tevador/RandomX), MIT) を用いる。
Rust からは C++ 参照実装への FFI で利用する。

```
pow_hash = RandomX(seed_hash, header_serialized)
有効条件: pow_hash (ビッグエンディアン u256 として解釈) ≤ target(difficulty)
```

### 11.2 動作モード

| モード | メモリ | 用途 |
| --- | ---: | --- |
| fast | 2 GB (共有) + 256 MB | マイニング |
| light | 256 MB | ノードの検証 |

フルノードは light モードで動作可能である MUST。
すなわち、ノード運用に 2 GB のデータセットは要求しない。**採掘するか
どうかと、検証できるかどうかは別である。**

**両モードは同じハッシュを返す MUST。** 違うのは速さと必要なメモリだけ
である。ここが崩れると、fast モードで掘ったブロックを light モードの
ノードが撥ねる。実装では試験
`oag-pow/tests/fast_mode.rs::the_two_modes_agree_on_every_hash` が
両モードの出力を突き合わせている。

fast モードは 2 GB のデータセットを構築して用いる。**構築に 1 分前後
かかる**ため、シードエポック ([§11.3](#113-シードエポック)) が変わる
たびに作り直す必要がある (2048 ブロック = 約 34 時間ごと)。
データセットは読み取り専用であり、プロトコル上は複数スレッドで共有して
よい。VM だけがスレッドごとに要る。

2 GB を確保できない場合は light モードで採掘してよい。速さは落ちるが、
掘れるブロックは同じである。

**スレッド安全性**: RandomX の VM は内部にスクラッチパッドを持つため、
複数スレッドで共有してはならない。並列に検証または採掘する場合は、
**スレッドごとに VM を持つ MUST**。light モードでもスレッドあたり
256 MB のキャッシュを要する点に注意する
(キャッシュ自体は共有可能だが、本実装は単純さを優先して共有していない)。

#### 複数スレッドで掘る

採掘スレッドは**ノンス空間を等分して**受け持つ SHOULD。64 ビットを
本数で割り、重ならない範囲をそれぞれが試す。当たりが 1 個出れば、
その土台での探索は全員が打ち切る。

先端が動いたら、配ってある土台は捨てる MUST。**捨てそこねた土台で
掘り当てたブロックは、1 つ前の先端に繋がる。** 出せば自分で分岐を
作ることになる。本実装は土台に世代番号を振り、食い違うものを捨てて
いる (`oag-miner` の `pool` モジュール)。

fast モードのデータセットは**全スレッドで 1 本を共有する SHOULD**。
スレッドごとに増えるのは VM のスクラッチパッド 2 MB だけである。light
モードは、本実装ではキャッシュを共有していないので本数の掛け算になる。

| モード | 1 スレッド | 4 スレッドなら |
| --- | ---: | ---: |
| light | 256 MB | 1 GB |
| fast | 2 GB | 2 GB |

検証用の light 検証器は採掘とは別に 1 個要る。採掘スレッドの採掘器を
検証に使い回すことはできない (VM はスレッドをまたげないため)。

> **本実装の作り**: `randomx-rs` 1.6.0 の `RandomXDataset` は生ポインタを
> 持つため `Send` ではない。そこで `oag-pow` の `SharedDataset` が包み、
> `unsafe impl Send / Sync` を 2 行だけ書いている。**ワークスペースで
> 自分が書いた `unsafe` はこの 2 行だけである。** `oag-pow` だけ
> `#![deny(unsafe_code)]` に下げ、他の crate は `#![forbid(unsafe_code)]`
> のままである。引き受けている事柄 (初期化後は読むだけ、RandomX 自身の
> ベンチマークが同じ使い方をしている、解放は `Arc` で 1 回だけ) は
> `SharedDataset` の説明にある。
>
> VM は包まない。**採掘器を渡さず、作り方を渡す**のは変わらない。作り方が
> `SharedDataset` を抱えてスレッドを越え、各作業スレッドがその上に自分の
> VM を建てる。経緯は [§19](#複数スレッドでの採掘はデータセットを共有する)。

### 11.3 シードエポック

RandomX のシードは一定間隔で切り替わる。Monero と同じ方式を採用する。

```
SEED_EPOCH_BLOCKS = 2048        (約 34 時間)
SEED_LAG          = 64 ブロック

seed_height(h) = ((h − SEED_LAG) / 2048) × 2048      (h ≥ 2048 + SEED_LAG の場合)
seed_hash      = seed_height のブロックハッシュ
```

エポックをこれより短くすると、マイナーが 2 GB のデータセットを再構築する
頻度が上がる (1 回あたり 1〜2 分) ため、実効ハッシュレートが低下する。

`SEED_LAG` は、リオーグによってシードが変化することを防ぐための猶予である。

**`seed_hash` は、検証しようとしているヘッダ自身の枝から引く MUST。**
アクティブチェーンの高さの索引から引いてはならない MUST NOT。headers-first
の同期 ([§14.5](#145-p2p-プロトコル)) では、ヘッダが高さ数千まで届いていても
本体が 1 つも繋がっていない時期があり、そのあいだアクティブチェーンの高さは
0 のままである。索引は知っているはずのシードにも「無い」と答える。

引けなかったときに別のハッシュで代用してはならない MUST NOT。鍵が違えば
RandomX は違うハッシュを返し、**正しいブロックの PoW が落ちる**。エポックの
境界で同期が止まり、そこから先へ進めなくなる。引けないのであれば誤りとして
返すこと。

### 11.4 FFI 境界で守ること

RandomX の実装は C++ である。Rust 側で `unsafe` を禁じても、それが縛る
のは自分が書いたコードだけであり、束ねている crate の中の `unsafe` も、
その先の C++ も縛らない。以下は実装が境界で守る MUST である。

**VM の NULL を検査する MUST。** C++ の `randomx_create_vm` は、VM の確保
(`vm->allocate()`) が例外を投げると `nullptr` を返す。スクラッチパッド
2 MB を確保できないとき、JIT が実行可能メモリを地図に載せられないときに
起きる。`randomx-rs` 1.6.0 はこの NULL を検査せず `Ok` に包むため、
**そのまま使うと最初のハッシュ計算で NULL 参照になり、ノードが落ちる**。
誤りとして返し、ノードは動き続ける MUST。

**JIT が使えない環境へ退避する SHOULD。** `randomx_get_flags` の推奨値は
`FLAG_JIT` を含む。JIT は実行可能メモリを要求するため、SELinux の
`deny_execmem`、PaX の MPROTECT、W^X を強制する容器などでは確保に失敗
する。RandomX にはインタプリタの経路 (`FLAG_DEFAULT`) があり、
実行可能メモリを要求しない。実装はフラグを

1. 推奨値 (JIT・ハードウェア AES 込み)
2. 推奨値から `FLAG_JIT` を外したもの
3. `FLAG_DEFAULT` (インタプリタ、ソフトウェア AES)

の順に試し、最初に通ったものを使う。**どの経路でも同じハッシュを返す
MUST** (フラグは速さの指定であって、計算するものは 1 つである)。ここが
崩れると JIT の有無でノードの合意が割れる。試験
`oag-pow/src/randomx.rs::every_flag_in_the_ladder_actually_produces_a_working_vm`
が全候補の出力を突き合わせている。

インタプリタは 10 倍ほど遅い。退避したことは運用者に伝える SHOULD。

**大きなページは試して、取れなければ退く SHOULD。** fast モードの
データセットは 2 GB の中を飛び回って読むので、4 KB のページでは TLB が
足りない。キャッシュとデータセットは、まず `FLAG_LARGE_PAGES` 付きで
確保を試み、失敗したら付けずに確保し直す。大きなページは OS 側の用意
(Linux の `vm.nr_hugepages`、Windows の「メモリ内のページのロック」権限)
が無ければまず取れないので、**取れないことを誤りにしてはならない**。
フラグは速さの指定であり、ハッシュは変わらない。

VM のスクラッチパッドには使わない。VM の確保に失敗すると NULL が返り、
下の規則により手放せなくなる。それが共有のデータセットの参照を抱えて
いれば、2 GB が二度と解放されない。同じ理由で、共有のデータセットに
VM を建てるフラグは、構築の前にキャッシュを使った light の VM で 1 度だけ
確かめて決めておく。

**NULL だった VM を解放してはならない MUST。** C++ の
`randomx_destroy_vm` は先頭で `assert(machine != nullptr)` している。
`NDEBUG` が立っていれば消える行だが、`cmake` crate は Rust のプロファイル
をそのまま持ち込むため、**`cargo test` の既定 (dev) では RandomX が
`CMAKE_BUILD_TYPE=Debug` で建ち、アサーションが生きている。** NULL の VM
を捨てるとその場で `abort` する。解放せずに手放すこと。抱えている
キャッシュやデータセットは漏れるが、ここに来るのは確保が失敗した場面
であり、ノードが落ちるよりはよい。

> なお dev ビルドの RandomX は最適化なしで建つため、**採掘も検証も
> 桁違いに遅い**。速さを測るときは `--release` を使うこと。

## 12. 難易度調整 (LWMA)

### 12.1 アルゴリズム

**LWMA-1** ([zawy12/difficulty-algorithms](https://github.com/zawy12/difficulty-algorithms))
を採用する。毎ブロック調整する。

```
T = 60                        目標ブロック時間 (秒)
N = 90                        窓幅
k = N × (N + 1) × T / 2

L = 0
sum_D = 0
for i in 1..=N:
    st = clamp(timestamp[i] − timestamp[i−1], −6×T, +6×T)
    L += st × i
    sum_D += difficulty[i]

if L < k / 10:
    L = k / 10                // 難易度の急騰を抑える下限

next_difficulty = (sum_D × k) / (N × L)
```

タイムスタンプの逆転 (負の solvetime) を許容し、クランプで扱う点が
LWMA の特徴である。

### 12.2 窓幅 N の検証

`N = 90` (90 分の窓) を採用する。以下は実装したシミュレーション
(`crates/oag-pow/src/lwma.rs` のテスト) による実測値である。
solvetime は指数分布に従わせ、乱数は決定的なため結果は再現する。

#### 定常状態

| 乱数種 | 平均ブロック間隔 | 難易度の最大振れ幅 |
| ---: | ---: | ---: |
| 1 | 60.55 秒 | 均衡値の 1.62 倍 |
| 2 | 60.51 秒 | 1.33 倍 |
| 3 | 60.50 秒 | 1.53 倍 |

目標 60 秒に対して 1 % 以内に収まっている。

#### ハッシュレート変動への追随

均衡難易度の誤差 20 % 以内に入るまでの所要。

| 変化 | ブロック数 | 実時間 |
| --- | ---: | ---: |
| 2 倍 | 31 | 0.20 時間 |
| **10 倍** | **99** | **0.70 時間** |
| 1/2 | 74 | 1.70 時間 |
| **1/10** | **145** | **5.64 時間** |

#### 非対称性という既知の弱点

上表のとおり、**ハッシュレートの増加には速く追随するが、減少からの回復は
遅い**。10 倍への追随が 0.7 時間なのに対し、1/10 への回復には 5.6 時間かかる。

これは PoW チェーン共通の性質である。ハッシュレートが失われるとブロック間隔が
伸びるため、難易度を下げるのに必要なブロック数を消化する実時間が長くなる。
窓幅を縮めれば回復は速くなるが、定常状態の振れ幅が大きくなる。

現実的な影響は、**大きなハッシュレートが一時的に流入して離脱すると、
その後数時間チェーンが遅くなる**ことである。小規模チェーンにとっては
実害のある性質であり、[§17](#17-相互運用性と-dex) で触れた
Monero とのマージマイニングは、この変動そのものを小さくする対策でもある。

本仕様は N = 90 を採用したうえで、この弱点を既知のものとして受け入れる。

### 12.3 立ち上げ期

```
height < N + 1  →  difficulty = GENESIS_DIFFICULTY (固定)
height ≥ N + 1  →  LWMA を適用
```

### 12.4 regtest は調整しない

| ネットワーク | 難易度調整 |
| --- | --- |
| mainnet | 行う |
| testnet | 行う |
| regtest | **行わない** (常に GENESIS_DIFFICULTY = 1) |

regtest では調整を行わない。行うと、ブロックを速く積むほど難易度が
上がってしまう。regtest の用途は試験であり、コインベースの成熟
(120 ブロック) を待つだけでも 120 個積む必要がある。目標の 60 秒間隔を
大きく下回る速さで積めば LWMA は正しく難易度を引き上げるため、
**積むほど遅くなり、試験が終わらない。**

Bitcoin の regtest (`fPowNoRetargeting`) と同じ扱いである。

**mainnet と testnet では必ず行う。** 行わなければハッシュレートの変動に
まったく追随できない。

## 13. 手数料ポリシー

### 13.1 二層構造

手数料は**コンセンサスルールではなくノードポリシー**として扱う。

```
コンセンサス層 (全ノードが強制、変更にハードフォークが必要)
  └ 手数料の下限を設けない。Σ入力 ≥ Σ出力 のみを要求する

ノードポリシー層 (各ノードの設定、いつでも変更可能)
  └ MIN_RELAY_FEE_RATE 未満のトランザクションは中継せず mempool にも保持しない
```

この分離により、OAG の価格変動に対して**ハードフォークなしで**
最低手数料を調整できる。

### 13.2 既定値

```
MIN_RELAY_FEE_RATE = 0.000005 OAG / バイト
                   = 50,000,000,000 atomic / バイト   (5 × 10^10)

基準トランザクション (195 バイト) の手数料 = 0.000975 OAG
```

### 13.3 ダスト閾値

未使用の UTXO はすべてのノードが恒久的に保持するため、
極小額の出力を大量生成する攻撃は全ノードのメモリを永続的に汚染する。

```
1 入力を消費するコスト = 102 バイト × 0.000005 = 0.00051 OAG
その 3 倍              = 0.00153 OAG
DUST_THRESHOLD        = 0.0015 OAG   (政策値として丸めた。倍率は約 2.94)
                      = 15,000,000,000,000 atomic  (1.5 × 10^13)
```

`DUST_THRESHOLD` 未満の出力を含むトランザクションは中継しない
(ノードポリシー。コンセンサスルールではない)。

### 13.3.1 未知の版数の扱い (ポリシー層)

[§10.4](#104-未知の版数の扱い) のとおり、未知の版数の出力はコンセンサス上
誰でも使用できる。ポリシー層では以下を既定とする。

- 未知の版数の出力を**作る**トランザクションを中継しない
- 未知の版数の出力を**使う**トランザクションを中継しない

前者は、有効化前のアドレスへ送金して資金を失う事故を防ぐためである。
後者は、そのような資金の横取りを助けないためである。

いずれもポリシーであり、マイナーが直接ブロックに入れることは妨げられない。

0.5.0 から、さらに次を既定とする。

- コミットメント出力 (版数 3、[§7.7](#77-コミットメント出力)) は、
  [§10.9](#109-ソフトフォークの有効化-採掘者の印) のソフトフォークが次の
  ブロックで有効なら、**作る**トランザクションを中継する。金額 0 なので
  ほこりの判定から外す。1 トランザクションに 1 個までとする。**使う**
  トランザクションは、有効化の前に作られたものも含めて中継しない。
- 65 バイトで末尾が `0x00` の署名 ([§8.3](#83-sighash-フラグ)) を含む
  トランザクションは、**有効化の前から**中継しない。
- リオーグで有効化の境目より前に戻ったら、mempool を組み直すときに
  コミットメント出力を持つものを落とす。

### 13.3.2 手数料を上げた置き換え (RBF)

すでに mempool にあるものと同じ UTXO を使うトランザクションは、以下の
すべてを満たせば、先に来たものを**追い出して**入る。追い出される側の
子孫も道連れになる。BIP125 の規則 2 から 5 にあたる。

| # | 規則 |
| --- | --- |
| 2 | 追い出す側に無かった**未確認の入力**を加えない |
| 3 | 手数料が、追い出す側 (子孫を含む) の**合計**以上である |
| 4 | その上乗せ分が `incremental_relay_fee_rate × 置き換えのサイズ` 以上である |
| 5 | 追い出す件数 (子孫を含む) が 100 以下である |

既定値は [付録 A](#付録-a-パラメータ一覧) に載せる。

#### 規則 1 (置き換え可能の表明) は適用しない MUST

BIP125 の規則 1 は、`sequence` によって「置き換えてよい」と表明した
トランザクションだけを置き換え可能とする。**本チェーンはこれを求めない。**
表明の有無にかかわらず置き換えは起こりうる。Bitcoin が最終的に落ち着いた
形と同じである。

理由は、表明が守れない約束だからである。

- 採掘者は手数料の高いほうを選べばよく、表明を見る義務はない
- 表明を見ないノードが 1 つでも中継すれば、置き換えは採掘者に届く
- したがって「表明していないから 0 承認で安全」は成り立たない

成り立たない保証を掲げると、それを信じた受け取り側が損をする。掲げない。

#### ゼロ承認のトランザクションを支払いとして受け取ってはならない MUST

RBF の有無にかかわらず成り立つ規則であり、RBF はそれを見えやすくした
だけである。受け取り側は承認を待つ。何承認待つかは
[§10.7](#107-受け取り側の確認数) に目安を置いた (既定 10)。

#### 規則 3 と 4 が見ているのは総額であること

料率ではない。したがって**大きくて料率の低い置き換えが、小さくて料率の
高いものを追い出せる**。追い出された側のほうが、ブロックに入る順番としては
先だったかもしれない。

これは BIP125 が抱えたままの弱点であり、Bitcoin も同じである。ここで
独自の規則を足すと、規則の緩いノードが中継したものを厳しいノードが
落とすことになり、mempool の中身がノードごとにばらける。**ばらけた
mempool は Compact Blocks の当たり外れに直結する**
([§14.9](#149-compact-blocks))。互換を優先する。

### 13.4 スパム耐性の評価

```
200,000 バイトのブロックを埋め尽くすコスト
  = 200,000 × 0.000005 = 1.0 OAG / ブロック
  = 1,440 OAG / 日
```

立ち上げ期において、これは十分に安価である。
これは PoW チェーン共通の性質であり、本仕様で解決するものではない。

### 13.5 チェーン成長の見積もり

```
200,000 バイト × 525,600 ブロック/年 = 約 105 GB/年 (満杯時)
```

したがって以下を v1 から実装する MUST。

- **プルーニング**: 検証済みの古いブロック本体を破棄し、
  UTXO セットとヘッダのみを保持するモード
- **UTXO スナップショット同期**: 新規ノードが全履歴を検証せずに
  参加できる経路 (Bitcoin の assumeutxo 相当)

命名規則: `testnet = mainnet + 10000`、`regtest = mainnet + 20000`。

#### 既存チェーンとの衝突回避

以下のポートは既存の主要チェーンが事実上占有しているため採用しない。

| ポート | 用途 |
| ---: | --- |

| 8232 / 8233 | Zcash |

特に **Bitcoin の 8333 を採用してはならない**。プロトコルの混線はマジックバイトに
よって防がれるため安全性の問題ではないが、以下の運用上の不利益を無償で相続する。

1. 同一ホストで Bitcoin ノードと同居できない
2. Bitcoin のピアゴシップとクローラから恒常的に接続試行を受ける

4. 一部のホスティング事業者のポリシーに抵触する

Bitcoin の regtest が 18444 を用いるため、本チェーンの testnet は 18444 ではなく
**19444** とする。

#### バインドアドレスの既定値

| サービス | 既定のバインド先 | 理由 |
| --- | --- | --- |
| P2P | `0.0.0.0` | 外部からの接続受け入れが前提 |
| **RPC** | **`127.0.0.1` のみ** | 資金操作が可能なため |
| **Mining** | **`127.0.0.1` のみ** | 同上 |

RPC を外部に公開した結果として資金を喪失する事故は、Bitcoin・Ethereum・Monero を
含む複数のプロジェクトで実際に発生している。既定値でこれを防ぐ MUST。

マイニング用インタフェースを RPC と分離する理由は、マイナーの接続を許可するために
RPC を外部公開せざるを得ない状況を構造的に避けるためである。
マイニング用インタフェースの中身 (Stratum) は [STRATUM.md](STRATUM.md) にある。
合意ルールの外の取り決めなので、本書には含めない。

### 14.2 マジックバイト

すべてのメッセージの先頭に置く 4 バイトである。ハンドシェイクの最初に
検証され、**ネットワーク間の分離を担う実質的な機構である**。ポート番号は
運用上の慣習にすぎず、分離を保証しない。

値は恣意的に選ぶのではなく、ネットワーク名から決定的に導出する。

```
magic = BLAKE3("Orange/network/<ネットワーク名>")[0..4]
```

| ネットワーク | 導出元 | 値 |
| --- | --- | --- |
| mainnet | `Orange/network/mainnet` | `33 97 55 03` |
| testnet | `Orange/network/testnet` | `7F 88 A0 C1` |
| regtest | `Orange/network/regtest` | `18 2C 9C 5E` |

いずれも印字可能な ASCII のみからは成らない。平文の流れの中に偶然
現れにくくするためである。

### 14.3 ジェネシス難易度

| ネットワーク | 難易度 |
| --- | ---: |
| mainnet | 1,000 |
| testnet | 10 |
| regtest | 1 |

**確定済みである。この値はジェネシスヘッダに入るため、変えるとジェネシス
ハッシュが変わり、別のチェーンになる。**

#### 低めに置いてある理由

LWMA は履歴が窓幅 (90 ブロック) に満たない間は働かない
([§12.3](#123-立ち上げ期))。すなわち**最初の 90 ブロックはジェネシス
難易度のまま**である。

- 高すぎた場合、公開直後にブロックが出ない。難易度を下げるには実際に
  ブロックが必要なので、**自力では抜け出せない**
- 低すぎた場合、最初の 90 ブロックが速く出るだけで、そのあと LWMA が
  引き上げる。発行が早まるのは最大 900 OAG (総発行量の 0.00009 %) である

取り返しがつくのは低すぎた側だけであり、低めに置く。

#### 参考値

難易度を決めるにあたって用いた値である。**実機の物理コアではこれより
速い。** 仮想化された環境で測ったものであり、上限ではない。

| モード | ハッシュレート | 難易度 1,000 での間隔 |
| --- | ---: | ---: |
| light (256 MB) | 約 30 H/s | 約 33 秒 |
| fast (2 GB) | 約 160 H/s | 約 6 秒 |

Intel Xeon 2.8 GHz の 1 コア、仮想化環境。RandomX のフラグは
`FLAG_HARD_AES | FLAG_JIT | FLAG_ARGON2_AVX2` である。

手元で測るには次を実行する。

```sh
cargo run --release -p oag-pow --features randomx --example hashrate
```

### 14.4 ジェネシスブロック

ジェネシスはチェーンの定義そのものである。ハッシュが変われば別のチェーンに
なるため、**一度確定させたら変更できない**。3 つのネットワークすべてで
確定済みである。

#### ジェネシスに PoW は無い

ジェネシスの PoW は検証しない MUST NOT。RandomX のシードは
[`seed_height`](#113-シードエポック) が示す高さのブロックハッシュであり、
高さ 0 ではそれがジェネシス自身のハッシュになる。**自分のハッシュを材料に
自分のハッシュを求めることはできない。** したがってジェネシスの nonce は
0 に置き、意味を持たせない。

ブロック 1 以降は、ジェネシスのハッシュをシードとして通常どおり検証する。

#### mainnet

| 項目 | 値 |
| --- | --- |
| ブロックハッシュ | `7511b77a9fb2aac8d7ba4655ed372c6fc3fbf800e1872a5c907bb64a775f0c40` |
| タイムスタンプ | 1,788,220,800 (2026-09-01T00:00:00Z) |
| コインベースのメッセージ | `Orange is good` |

#### ブロック 0 の報酬の扱い

mainnet と testnet では、ブロック 0 の 10 OAG を**発行したうえで焼却する**。

```
出力: 10 OAG → lock { version: 0, payload: 00×32 }
アドレス表記: oag1qqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqq6v5r6p
              toag1qqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqq3rsa95
```

32 バイトすべて 0 は secp256k1 の x-only 公開鍵として無効である
(x = 0 に対応する曲線上の点が無い)。使おうとすると署名の検証手前で
公開鍵の読み取りが失敗し、断られる。

**版数 0 であることが本質的である。** 未知の版数は誰でも使える
([§10.4](#104-未知の版数の扱い)) ため、そちらに落ちていたら焼却にならない。

「受け取らない」(出力を持たない) との違いは、**発行された事実が台帳に残る**
ことである。UTXO セットに 1 件残り、エクスプローラでは焼却先アドレスに
10 OAG が置かれたまま見える。誰も取っていないことが見える形で示される。
発行総量から見れば 0.000001 % である。

### 14.5 P2P プロトコル

**独自実装**とする。rust-libp2p は採用しない。

PoW チェーンの P2P 要件は「ブロックとトランザクションの伝播」に尽き、
libp2p の DHT や多様なトランスポートはオーバースペックであり、
依存の重さと仕様変更の追随コストが利益を上回ると判断した。

実装する機能:

- ハンドシェイク (`version` / `verack`)
- ピア探索 (シードノード + アドレス交換)
- `inv` / `getdata` によるブロックとトランザクションの伝播
  (下記「中継の規則」)
- **headers-first 同期**

- **Compact Blocks** — [§14.9](#149-compact-blocks) を参照。v1 から必須とする

#### 提供機能の名乗り (services)

`version` の `services` は、そのノードが**何を配れるか**の申告である。

| ビット | 名前 | 意味 |
| --- | --- | --- |
| — (0) | `SERVICE_NONE` | 何も配れない。ヘッダしか持たない |
| `1 << 0` | `SERVICE_FULL_NODE` | **創世から**すべてのブロックを配れる |
| `1 << 1` | `SERVICE_LIMITED` | 直近のブロックだけ配れる (剪定ノード) |

**一部でも配れないノードが `SERVICE_FULL_NODE` を名乗ってはならない
(MUST NOT)。** どこまで遡れるかは名乗りに含まない。求められたブロックを
持っていなければ `notfound` を返す (上記「持っていないと言われたら」)。

##### 版数 1 の `services` は未定義である

プロトコル版数 1 のノードは、この欄を常に 0 のまま送っていた。

**版数 1 を話す実装はフルノードしか存在しなかった。** したがって版数 1 の
相手は、`services` の値にかかわらず `SERVICE_FULL_NODE` として扱う
(MUST)。これは推測ではなく、その版数で軽量ノードも剪定ノードも公開された
ことがないという事実による。

0 を額面通り「何も配れない」と読んではならない。読めば、稼働中の
フルノードが軒並み軽量ノード扱いになる。**申告された 0 と未記入の 0 は、
版数でのみ区別できる。**

`services` が意味を持つのは**版数 2 以降**である。

##### 申告であって保証ではない

相手は嘘をつける。配れないのに `SERVICE_FULL_NODE` を名乗ることを、
プロトコルは妨げない。名乗りは**繋ぎ先を選ぶための手がかり**であって、
信用の根拠ではない。応じない相手は `notfound` と時間切れで他へ回る。

伝え聞いた名乗りは記録しない (SHOULD NOT)。`addr` で配られる `services` は
第三者についての伝聞であり、偽れる。**自分でハンドシェイクして確かめた
値だけを住所帳に控える。**

#### 同期の手順

headers-first である。まずヘッダだけを集めてチェーンの形を確かめ、
そのうえで本体を取り寄せる。ヘッダは本体の 1/2000 の大きさで、PoW と
繋がりを検証できる。先にこれを集めてしまえば、**どのブロックが本当に
必要かが分かってから本体を求める**ことになる。順に本体を要求していく
方式では、無関係なブロックを延々と送りつけられる。

```text
1. getheaders (ロケータ)  ──▶
2.                        ◀──  headers (最大 2000 件)
   ヘッダを検証し、インデックスに載せる (本体は無い)
3. getdata (本体が要るもの) ──▶
4.                        ◀──  block
   本体を検証し、アクティブチェーンに繋ぐ
```

新しいブロックを掘った側は `inv` で知らせる。受け取った側は
**ハッシュだけでは高さも繋がりも分からない**ため、本体を直接求めるの
ではなく `getheaders` からやり直す。

#### 持っていないと言われたら、直ちに他の相手へ回す

`getdata` に対して相手が `notfound` を返したら、その依頼を**直ちに待ち
行列へ戻さなければならない (MUST)**。時間切れを待ってはならない。

先端を `inv` で知らせてくれた相手と、本体を頼む相手は同じとは限らない。
本体は繋がっている相手に均して頼むので、**まだそのブロックを持っていない
相手に当たること自体は避けようがない。** 避けられない以上、断られたときに
直ちに回し直せなければならない。返事が来ているのに時間切れまで待つと、
その間そのブロックは誰にも頼めない。ブロックは親から順にしか繋げないので、
止まるのはその 1 個では済まず、**後続をいくら集めても繋げられない。**

戻すのは**頼んだ相手からの `notfound` だけである (MUST)**。誰のものでも
効くようにすると、無関係なピアが `notfound` を送るだけで他人への依頼を
剥がせる。

トランザクションは戻さない。1 度で諦めると決めてあるため (後述)、戻した
ところで次に頼む先がない。

#### 中継の規則

**検証してから伝える MUST。** 受け取ったものをそのまま横へ流しては
ならない。流してよいのは、自分で検証を通したものだけである。

| 対象 | 流す条件 | 流す形 |
| --- | --- | --- |
| ブロック | 検証を通り、**アクティブチェーンの先端が動いた** | `inv` |
| トランザクション | mempool に受け入れられた | `inv` |

実体 (`block` / `tx`) を押し付けてはならない。知らせるのはハッシュだけ
であり、要る側が `getdata` で求める。押し付ける形では、相手が要らない
ものを送りつけられる。

**くれた相手には流し返さない SHOULD。** 相手は既に持っている。害は
ないが、往復が無駄である。

置き換え ([§13.3.2](#1332-手数料を上げた置き換え-rbf)) も同じ条件で流す。
mempool が受け入れたなら新しい txid を `inv` で知らせる。**追い出された
txid を「消えた」と知らせる手立ては無い。** 各ノードが自分で同じ判断に
至るか、あるいは至らないだけである。これは伝えられる情報ではなく、
「ゼロ承認のトランザクションを支払いとして受け取ってはならない」という
規則の根拠のひとつである。

先端が動かなかったブロック (作業量の少ない側の枝) は流さない。
**流さなくても失われない。** その枝が後に最長になれば、そのときの
新しいブロックが先端を動かし、そこから `getheaders` で辿れる。

#### 伝播に TTL は設けない MUST

ばら撒き型のネットワークで跳ね回数の上限を設けてはならない。上限より
遠いノードにはブロックが永久に届かず、**恒久的なチェーン分裂になる**。
ネットワークの直径は分からず、ノードの出入りで変わるため、正しい値を
選ぶことはできない。収束は累積作業量で決めるものであり、跳ね回数の
予算で決めるものではない。

伝播が止まるのは**状態**による。すでに持っているブロックは先端を
動かさないので中継されない。すでに mempool にあるトランザクションは
受け入れられないので中継されない。波は、知っているノードに当たった
ところで消える。

置き換えも同じである。置き換えを済ませたノードは、同じものをもう一度
受け入れない (`AlreadyKnown`)。手数料を上げ続ければ何度でも波を起こせるが、
1 回ごとに規則 4 の上乗せを払う。**代金が跳ね回数の上限の代わりをする。**

無限に流れ続けることを防ぐのは、TTL ではなく次の各項である。

| 縛るもの | 手段 |
| --- | --- |
| 同じものが回り続ける | 重複は中継しない (上記) |
| 頼んでいない実体が届く | `inv` → `getdata` の引き寄せ型 |
| 1 通で運べる件数 | `inv` / `getdata` は 5,000 件、`headers` は 2,000 件 |
| 1 通の大きさ | 1 MiB ([§14.7](#147-メッセージの枠組み)) |
| 同時に頼む数 | ブロック 16 件、トランザクション 32 件 (ピアごと) |

#### 頼んでいないトランザクションは検証しない MUST

`tx` を受け取ったら、**そのピアにその txid を頼んであったかを先に
確かめる**。頼んでいなければ、中身を見ずに捨てる。

署名の検証は高い計算である。誰でも `tx` を送りつけられる状態では、
繋がっただけの相手がこちらの CPU を好きなだけ使える。`inv` で知らされ、
こちらが `getdata` で求めた分だけを検証する。

頼んだ記録は**使い切り**である。受け取った時点で消える。同じピアが
同じものを続けて送っても、2 通目からは通らない。

時間切れになった依頼は**忘れる。頼み直さない SHOULD。** ブロックは
1 つ欠けると以降が繋がらないので頼み直すが、トランザクションにその
制約はない。存在しない txid を大量に知らされたとき、頼み直す作りだと
ピアを変えながら同じ嘘を追い続けることになる。

#### 受け付けなかったときの扱い

| 対象 | 検証に落ちたら |
| --- | --- |
| ブロック | **接続を切る MUST** |
| トランザクション | 捨てる。切ってはならない MUST NOT |

ブロックの検証規則はコンセンサスであり、落ちるものを送ってくる相手は
規則が違うか、悪意がある。どちらにせよ繋がっている意味がない。

トランザクションが受け付けられない理由には無害なものが多い。手数料が
こちらの方針に足りない、同じ UTXO を使う別のものを先に持っている、
など ([§13](#13-手数料ポリシー) の方針層)。**方針の違いで接続を切ると、
ネットワークが方針ごとに割れる。**

#### ブロックの三つの状態

インデックスの各ブロックは次のいずれかである
([§10.2](#102-ブロックの検証))。

| 状態 | 意味 | 先端の候補になるか |
| --- | --- | --- |
| ヘッダのみ | ヘッダと PoW を検証済み。本体は無い | ならない |
| ヘッダ有効 | 本体はあるが、まだ接続していない | なる |
| 完全有効 | 本体を検証し、接続したことがある | なる |
| 無効 | 検証に失敗した。子孫もすべて無効 | ならない |

先端を切り替える前に、**アクティブチェーンに合流するまでの経路が
すべて本体を持っていること**を確かめる。取り寄せは複数のピアに割り振る
ため、本体は順序が入れ替わって届きうる。途中が欠けたまま先へ進むと、
検証していないブロックを飛ばして UTXO を更新することになる。

### 14.6 ピア発見

#### シードノード

| ネットワーク | ホスト名 |
| --- | --- |
| mainnet | `seed.oagcoin.org`、`oagnode.vslabs.co.in` |
| testnet | `testnet-seed.oagcoin.org` |
| regtest | なし |

ホスト名を引くと、稼働中のノードの IP が A / AAAA レコードで返る。
ポートはそのネットワークの既定値を用いる (DNS にポートは書けない)。

**シードを引くのは、次のいずれかのときだけである MUST。**

- 住所帳に候補が 1 件も無く、かつ外向きの接続が 1 本も無い
- 先端が 30 分動かない ([§14.8](#148-ハンドシェイク) の生存確認を参照)。
  30 分に 1 回まで
- 追いついていて (同期の最中でない)、外向きの接続が目標の 8 本に足りず、
  住所帳に候補が 1 件も無い。追いついた直後に 1 回、その後は 30 分に
  1 回まで (0.1.4 から)

3 つ目は、同期の最中は 2 本しか繋がないために、住所帳が薄いまま追いつく
ことがあるからである。当てが無ければ 8 本まで足せず、2 本のまま居続ける。

繋がったあとはノード同士が住所を教え合うので、シードは常用しない。
したがってシードが落ちても既存のネットワークは死なない。困るのは新しく
入ろうとするノードだけである。

シードの答えは信用しない。DNS は平文で運ばれ、経路上で書き換えられる。
シードから得た住所も、他のピアから聞いた住所と同じ扱いにする MUST。

regtest にシードは置かない。手元で試すためのものであり、公開ネットワーク
ではない。

#### 住所帳

覚えた住所はデータディレクトリの `peers.json` に残す。構造は Bitcoin の
`addrman` と同じ**二表**である。

| 表 | 中身 | バケット数 | 1 バケット | 合計 |
| --- | --- | ---: | ---: | ---: |
| `new` | 聞いただけの住所 | 1,024 | 64 | 65,536 |
| `tried` | 実際に繋がった住所 | 256 | 64 | 16,384 |

| 項目 | 値 |
| --- | ---: |
| 1 つの出どころ (/16) が触れる `new` バケット数 | 64 |
| 同じ /16 が触れる `tried` バケット数 | 8 |
| 1 つの住所が `new` で占めうる枠 | 8 |
| 1 通の `addr` で受け取る上限 | 256 件 |
| `getaddr` に返す上限 | 256 件 |
| 配らなくなるまでの期間 | 30 日 |
| 再試行までの間隔 | 1 分から倍々、6 時間で頭打ち |

住所帳は**相手が中身を決める記憶域**である。`addr` で送られてきた住所を
溜めるので、攻撃者は好きな住所を送り込める。狙いは日蝕攻撃であり、
住所帳を手下で埋め尽くして正直なノードに繋がらせず、見せるチェーンを
攻撃者が選ぶ。

##### `new` から `tried` への昇格には接続の成功を要求する MUST

`addr` を送りつけるだけでは `tried` に入れない。これが二表構造の要である。

##### 外向きの接続先は `new` と `tried` から半々で引く MUST

**`new` が丸ごと攻撃者のものであっても、外向きの接続の半分は実績のある
相手に向かう。** 埋め尽くしが効かなくなるのはこの一点による。

##### バケットはノードごとの秘密の鍵と一緒に決める MUST

住所そのものからバケットを決めてはならない。決められる形だと、狙った
バケットを埋める住所を用意される。鍵は住所帳と一緒に保存する
MUST。**起動のたびに変えてはならない。** 変えれば、その都度すべての住所が
別のバケットへ散り、表の中身が意味を失う。

攻撃者が占められる枠には、構造そのものが上限を与える。

| 表 | 何で括るか | 触れるバケット | 全体に占める割合 |
| --- | --- | ---: | ---: |
| `new` | **教えてきた相手**の /16 | 64 / 1,024 | 6.25 % |
| `tried` | **住所自身**の /16 | 8 / 256 | 3.1 % |

住所を大量に用意するより、**別々のネットワークを大量に用意するほうが
ずっと高くつく**、という前提に立つ。

##### その他の規則

- **元気な先客を押しのけない MUST。** 枠が塞がっているとき、押しのけて
  よいのは見込みの尽きた住所だけである。繋がるノードを並べるだけで表を
  入れ替えられるようにしてはならない。`tried` の行き先が塞がっていて
  先客が元気なら、**昇格しない**で `new` に留まる
- **繋がった住所を `new` の空きに依存させない MUST。** 実際に接続できた
  住所は、`new` に枠が取れなくても `tried` へ入れる。`new` は**まだ試して
  いない住所**の置き場であり、繋がった相手がそこの枠を取り合う理由がない。
  要求すると、**聞かせた住所で `new` を埋めるだけで、正直な相手が `tried`
  に入るのを塞げる**。二表に分けてあるのは実績のある相手を別勘定にする
  ためであり、片方を埋めてもう片方への道を塞げるなら分けた意味がない。
  ただし上の「元気な先客を押しのけない」は変わらない。`tried` の行き先が
  塞がっていて先客が元気なら迎えず、そのときはどちらの表にも属さない
  項目を残さない
- **配るのは `tried` の住所だけ MUST。** 聞いただけの住所を配ると、
  こちらが裏書きして広めることになる。Bitcoin は `new` からも配るが
  本実装は配らない。その分、まだ誰も繋いだことのない新しいノードの住所は
  1 ホップで止まる。**止まったままにはならない。** 聞いた側は `new` からも
  半分の割合で繋ぎに行くので、繋がった時点で `tried` に上がり、そこから
  配られ始める
- **未来のタイムスタンプを受け入れない MUST。** 見限る判定が古さを見るので、
  許すと未来を名乗る住所が居座る
- **公開ネットワークでは到達できない住所を覚えない MUST**
  (ループバック、private、CGNAT、リンクローカル、ドキュメント用)。
  regtest は手元で 2 台繋ぐために許す
- **IPv4 射影アドレスは IPv4 として判定し、括りもバケットも IPv4 と
  共有する MUST。** 二重に持つと同じ相手が枠を 2 つ取れる

##### 見限る条件

次のいずれかで見込みが尽きたとみなし、枠が要るときに真っ先に譲る
(Bitcoin の `IsTerrible` と同じ)。

- 最後に見かけてから 30 日を過ぎた
- 一度も繋がらないまま 3 回続けて失敗した
- 最後に繋がってから 7 日を過ぎ、かつ 10 回続けて失敗した

ただし**直前 1 分以内に繋ぎに行っていれば見限らない**。結果が出る前に
捨てると、いま繋ぎに行った先が即座に消える。

#### 接続の維持

外向きの接続を 8 本保つ。住所帳は同じ /16 から候補を 1 件しか返さない
ので、この本数はそのまま**別々のネットワークの数**になる。

**相手から繋がれた接続は本数に数えない MUST。** 数えると、繋いでくる
だけで外向きの接続を止められる。

#### 住所の伝わり方

1. こちらから繋いだ相手に `getaddr` を送る。**相手から繋がれた接続には
   送らない** (誰でも開ける接続から住所を集めると、攻撃者が聞かれる側に
   回りやすい)
2. `getaddr` に応えるのは **1 本の接続につき 1 度だけ MUST**。繰り返し
   応えると住所帳を丸ごと吸い出す道具になる
3. 新たに到達を確かめた住所は、繋がっているピアに `addr` で流す。
   あとから判明した住所はこの経路で伝わる
4. 自分の住所は、運用者が明示した場合か、ルーターがポートを開けて外側の
   住所を告げた場合にのみ名乗る。**自分の外向きの住所を自分で確かめる
   手立ては無い**。ルーターの答えも同じ LAN の誰でも偽れる。偽られても
   起きるのは届かない住所を名乗ることだけで、それは 3 の規則 (繋がって
   初めて配られる) により広まらない

#### ルーターに開けてもらう

家庭のルーターの内側にいるノードは、外から繋がれない。数が増えても繋ぎ
先にならない。`oag-node` は起動時に UPnP IGD で、答えが無ければ NAT-PMP
(RFC 6886) で、待ち受けのポートを開けてもらう。

- 開けてもらえたら、ルーターが告げた外側の住所とポートを名乗る
- 外側の住所が公開の住所でなければ (CGNAT など) 名乗らず、閉じてもらう
- 期限付きで頼み、期限の半分で頼み直す。期限付きに応じない機器には
  永続で頼み、終了時に閉じてもらう
- 運用者が住所を明示したとき、待ち受けないとき、軽量モード、regtest、
  自分の住所がもともと公開の住所のときは頼まない
- `--no-portmap` で止められる

**既定で頼む。** 繋がれるノードを増やすのが目的であり、選んで付ける形に
すると付ける人がほとんどいない。

### 14.7 メッセージの枠組み

```
magic     [4]   ネットワーク識別子
command  [12]   コマンド名。ASCII 小文字、余りは NUL 埋め
length    [4]   ペイロード長 (u32 LE)
checksum  [4]   BLAKE3(payload)[0..4]
payload  [長さ]
```

前置きは 24 バイトである。

#### 長さの検査は読み込む前に行う MUST

宣言されたペイロード長が上限を超えていたら、**ペイロードを 1 バイトも
読まずに接続を切る**。長さだけを大きく偽って接続を保つことで、相手の
メモリを枯渇させる攻撃を防ぐため。

```
ペイロード長の上限   1 MiB
```

最大のブロック (200,000 バイト) と、上限まで詰めた `inv`
(5,000 項目 × 33 バイト = 165,000 バイト) の双方が余裕をもって収まる。

#### 項目数の上限

| メッセージ | 上限 |
| --- | ---: |
| `inv` / `getdata` / `notfound` | 5,000 項目 |
| `headers` | 2,000 件 |
| `addr` | 1,000 件 |
| `getheaders` のロケータ | 64 件 |
| ユーザエージェント | 64 バイト |

### 14.8 ハンドシェイク

```
自分 ──version──▶ 相手
自分 ◀──version── 相手
自分 ──verack───▶ 相手
自分 ◀──verack─── 相手
```

両方向がそろって初めて通常のやり取りに入る。**完了前に本題のメッセージを
受け取ったら接続を切る MUST**。名乗っていない相手にブロックを配らないため。

`version` に含める乱数は自己接続の検出に用いる。相手の `version` に自分と
同じ乱数が入っていたら、それは自分自身への接続である。

#### 生存確認 (0.1.2 から)

TCP は、相手が黙って消えたこと (電源断・スリープ・NAT の期限切れ) を
報せない。何も送らずに待つと、死んだ接続を繋がっていると思ったまま
待ち続ける。0.1.1 までは実際にそうなり、ピアが 1 本のノードが 37 分間
ブロックを受け取らなかった。

- ハンドシェイクのあと、60 秒ごとに `ping` を送る。返事を待っている間は
  重ねて送らない
- `ping` を受けたら同じ nonce で `pong` を返す MUST (0.1.0 から)
- 待っている nonce の `pong` が 300 秒来なければ切る。違う nonce や、頼んで
  いない `pong` では生きていることにしない
- 1 通を 120 秒で送り終えられなければ切る
- 先端が 300 秒動かなければ、相手に `getheaders` を送り直す。相手の `inv`
  を取りこぼしていても追いつける
- 先端が 30 分動かなければ、シードを引き直して繋ぎ先の候補を足す
  ([§14.6](#146-ピア発見))

外向きの接続が切れれば、住所帳から補充される。`--no-discovery` で名指し
した相手は、切れたら 5 秒後に繋ぎ直す。

#### 同期の最中 (0.1.2 から)

知っているヘッダより、繋いだ本体が 16 ブロックを超えて遅れている間を
同期の最中とする。その間は次のようにする。

- 繋がれても応えない。名乗り合う前に閉じる
- 外へは 2 本しか繋がない。追いついたら 8 本まで足す。先端が 30 分
  動かなければ、同期の最中でも制限を外す
- `--external-addr` の住所を名乗らない

**先端の古さでは決めない。** 誰も掘らない時間が続いたあとに全員が再起動
すると、全員の先端が古くなる。古さで決めると全員が同期の最中になって
誰も繋がれなくなり、ネットワークが立ち上がらない。先を知っているのに
追いついていないときだけを同期の最中とすれば、先を知らせてくれた相手が
必ずいるので、そうはならない。

### 14.9 Compact Blocks

ブロックを丸ごと送らず、**相手がすでに持っているものは送らない**。

```
cmpctblock
  header      100 バイト
  nonce         8 バイト
  短縮 ID       6 バイト × (取引数 − 埋め込んだ数)
  埋め込み取引  コインベースは相手が持たないので必ず含める
```

受け取った側は mempool から短縮 ID の一致するものを拾い、足りない分だけ
`getblocktxn` で番号を指定して求める。

#### 実測

`crates/oag-net/src/compact.rs` の試験による実測値である。

| ブロック内の取引数 | `block` | `cmpctblock` | 比 |
| ---: | ---: | ---: | ---: |
| 10 | 1,710 B | 270 B | 6 |
| 100 | 15,300 B | 810 B | 19 |
| 500 | 75,701 B | 3,211 B | 24 |
| **1,000** | **151,201 B** | **6,211 B** | **24** |

10 Mbps の回線で 1,000 件のブロックを送り出す時間は **121 ms から 5 ms**
になる。

#### なぜ 60 秒ブロックで重要か

伝播に時間がかかるほど、同じ高さのブロックが並行して掘られる確率
(孤児率) が上がる。孤児率が高いと、接続の良い大規模なマイナーが有利になり
中央集権化が進む。[§7.2](#72-標準トランザクションのサイズ) で見たとおり、
本チェーンは 200,000 バイトを 60 秒間隔で撒くため、これがないと孤児率が
2〜3 % に達する。

#### 短縮 ID の衝突

短縮 ID は 6 バイトしかないため、mempool の中の無関係な取引と偶然一致
しうる。その場合、組み立てたブロックは**間違ったものになる**。

**組み立ての最後に必ずマークルルートを検証する MUST。** 合わなければ捨てて
通常の `block` を求め直す。これにより、衝突も、相手が誤った取引を返した
場合も捕まる。

短縮 ID の鍵はブロックごとに変わる。

```
key      = BLAKE3("OAG/cmpct/shortid" || header || nonce)
short_id = BLAKE3_keyed(key, txid)[0..6]
```

鍵が固定であれば、攻撃者が衝突する取引をあらかじめ用意して全ノードを
一斉に妨害できてしまう。ブロックごとに変えることでこれを防ぐ。

### 14.10 ストレージ

**redb** (純 Rust の埋め込み ACID データベース) を用いる。

rocksdb は実績で勝るが C++ 依存でクロスコンパイルが煩雑になる。
UTXO セットの規模において redb の性能は十分と判断した。

## 15. RPC

取引所やブロックエクスプローラが繋ぎこむ口である。**JSON-RPC 2.0 over
HTTP**とする。bitcoind と同じ形であり、最も広く通じる。

### 15.1 締め出し

| 項目 | 既定 |
| --- | --- |
| バインドアドレス | **ループバックのみ** (127.0.0.1) |
| 認証 | 必須。HTTP Basic |
| 合言葉 | 起動のたびに作り、データディレクトリの `.cookie` に書く |
| `.cookie` の権限 | 所有者のみ読み書き可 (0600) |

RPC を外部公開した結果として資金を喪失する事故は複数のプロジェクトで
起きている。**既定値でこれを防ぐ** ([§14.1](#141-ポート))。

合言葉は起動のたびに作り直す。設定ファイルに書かせると、そのファイルが
複製され、履歴に残り、共有される。使い捨てにすれば、漏れても次の起動で
無効になる。

### 15.2 HTTP として受け付ける範囲

必要なのは「`POST /` に JSON の本文を 1 個」に尽きる。**受け付ける範囲を
狭く保つこと自体が守りである。**

- メソッドは `POST`、パスは `/` のみ
- `Content-Length` が必須。`Transfer-Encoding` は断る
  (読み終わりを相手任せにすると、いくらでも送り続けられる)
- 宣言された長さは**読む前に**検査する
- ヘッダは 8 KiB、本文は 4 MiB まで
- 認証は**手続きを呼ぶ前に**確かめる
- 合言葉の突き合わせは**かかる時間が中身に依らないようにする**。
  素朴な比較は最初に違ったところで止まるため、1 バイトずつ試して応答の
  速さを測れば先頭から当てていける

### 15.3 手続き

| 名前 | 引数 | 返すもの |
| --- | --- | --- |
| `getinfo` | なし | ネットワーク・高さ・先端・難易度など |
| `getblockcount` | なし | アクティブチェーンの高さ |
| `getbestblockhash` | なし | 先端のブロックハッシュ |
| `getblockhash` | `[高さ]` | その高さのブロックハッシュ |
| `getblockheader` | `[ハッシュ]` | ヘッダの中身と検証状態 |
| `getblock` | `[ハッシュ, 詳細=true]` | ブロック。`false` なら 16 進 |
| `getrawtransaction` | `[txid, 詳細=false]` | 取引。索引が無ければ mempool のみ |
| `getaddresshistory` | `[アドレス, 開始=0, 件数=100]` | そのアドレスに触れた取引 |
| `getindexinfo` | なし | 索引を持っているか |
| `getmempool` | なし | mempool の txid 一覧 |
| `sendrawtransaction` | `[16 進]` | 受理された txid |
| `scanutxos` | `[[アドレス, …]]` | 一致する UTXO と合計 |

金額は `u128` であり JSON の数値では表しきれない。**atomic 単位の 10 進
文字列**で返す。累積作業量も同様である。

#### 索引を要する手続き

`getaddresshistory` と、`getrawtransaction` が確定した取引を引く動作は、
**任意機能である索引に頼る** (→ [§19 の決着した項目](#決着した項目))。
索引を持たないノードでは使えない。

**その場合は空の答えではなく誤りを返す。** 「見つからない」と答えると、
呼び出し側はそれを「その取引は存在しない」と受け取る。持っていないことと
無いことは別であり、区別を消してはならない。索引の有無は `getindexinfo`
で分かる。

索引を持たないまま確定した取引を引くには、それが入っているブロックを
`getblock` で取り、その中から探す。

#### `scanutxos` が全件走査であること

支払い条件から UTXO を引く索引も持たない。ウォレットは UTXO セットを
丸ごと見て自分のものを拾う。bitcoind の `scantxoutset` と同じ方式である。

走査には上限があり、達した場合は `truncated: true` を返す。**呼び出し側は
これを見なければならない。** 見ずに合計を残高として表示すると、実際より
少なく見せることになる。

### 15.4 エクスプローラ

ブラウザで鎖の中身を見るための、**読むだけ**の HTTP を別に持つ。既定の
待ち受けは `127.0.0.1:8080` である。

#### RPC の口を使い回さないこと

[§15.2](#152-http-として受け付ける範囲) の口は「`POST /` に JSON を 1 個、
合言葉つき」しか受け付けない。**その狭さがあの層の安全性そのものである。**
`GET` と任意のパスを通すために広げれば、資金を動かせる入口の作りを弱める
ことになる。

エクスプローラは読むだけで、状態を変える経路を一切持たない。別の口として
分けておけば、片方を緩めてももう片方は緩まない。

#### 受け付ける範囲

- 動詞は `GET` と `HEAD` のみ。ほかは断る
- 経路は `/`、`/block/<高さ|ハッシュ>`、`/tx/<txid>`、`/address/<アドレス>`、
  `/mempool`、`/stats`、`/richlist`、`/peers`、`/search?q=`、`/api/stats`
- 要求の頭は 8 KB まで。1 要求 1 接続とする

**経路もクエリも利用者が決める文字列である。** 頁に埋める値はすべて逃がす。
局所で動かすものであっても、逃がさなければ任意の script を仕込める入口に
なる。

#### 索引が無いときに黙らないこと

取引とアドレスの照会は索引に頼る ([§19](#決着した項目))。索引を持たない
ノードでは、**空の履歴ではなく「持っていない」と表示する**。空を見せると
利用者はそれを「取引が無い」と受け取る。ブロックの閲覧は索引なしでもできる。

#### 統計 (`/stats`、`/richlist`)

稼働日数 (ブロック 1 から)、平均のブロック間隔、ハッシュレート、残高を
持つアドレスの数、採掘したことのあるアドレスの数、直近 7 日に採掘した・
受け取ったアドレスの数、取引の数を出す。

**保有の分布も隠さずに出す。** 最も多く持つアドレス 1 件・上位 10 件・
上位 100 件の割合、残高帯ごとのアドレス数と金額、`/richlist` に上位 100 件。
偏りは見せないほうが疑われる。見せて、薄まっていく推移を示すほうがよい。

日ごと (UTC) の推移を折れ線で出す。ハッシュレート、採掘したアドレスの数、
その日の終わりに残高を持つアドレスの数、上位 1 件と 10 件の割合、取引の数。
同じ数字を表でも出す。**頁は JavaScript を持たない。** 線は SVG、目盛りと
日付は HTML に置き、値は各日の列の `<title>` に持たせる。

- **ハッシュレートは推定である。** 1 ブロックに要るハッシュ数の期待値は
  難易度そのものなので、直近 n ブロックの難易度の和をその n ブロックに
  かかった時間で割る。n は 60 (約 1 時間) と 1440 (約 1 日)。1 ブロック
  だけで割ると運に振り回される
- **アドレスの数は人の数ではない。** 1 人が多くのアドレスを持ちうるし、
  複数人が 1 つを共有しうる。そう頁に書く
- ジェネシスはどの数にも入れない。時刻は鎖が動き出した時刻ではなく、
  報酬は焼却されている
- 数えたところまでを覚えておき、次は新しいブロックの分だけ足す。覚えた
  先端が鎖から外れていれば数え直す
- 日ごとの保有はその日の終わりの残高から出す。ノードの UTXO セットは今の
  姿しか持たないので、**出力の出入りを自分で追う**。持つのは使われていない
  出力の支払い先と金額だけで、大きさは UTXO セットと同じ程度である
- 時刻は前後しうる。前の日付に見えるブロックは今の日に入れ、閉じた日は
  開き直さない

#### JSON (`/api/stats`)

外の集計サイト (採掘の収益計算など) が読むための口である。`/stats` の
「chain」の欄と**同じ値を同じ計算から**出す。計算は 1 か所に置き、頁と
JSON が別々に数えて食い違うことを防ぐ。項目と単位は `docs/COMMANDS.md` に
ある。

- **名前と単位は一度出したら変えない。** 変えると読んでいる側が壊れる。
  足すのは構わない
- 測れない値 (ブロックが足りないときのハッシュレートなど) は 0 ではなく
  `null` にする。0 は「誰も掘っていない」と読まれる
- 金額は OAG の十進の文字列で出す。1 OAG は最小単位の 10^16 個なので、
  最小単位の数は倍精度の浮動小数点数で正確に表せない (2^53 ≈ 9 × 10^15)
- どこからの読み出しも許す (`Access-Control-Allow-Origin: *`)。読むだけの
  公開の数字なので、許して困るものは無い
- 知らない `/api/…` には、HTML ではなく `{"error": …}` で答える

#### ピア (`/peers`)

エクスプローラを載せたノードが、いまハンドシェイクを済ませているピアを
出す。**ネットワーク全体の一覧ではない。** 頁にもそう書く。

接続の数 (外向き・内向き)、住所帳に覚えている住所の数、版ごとのピアの数、
ソフトフォークを強制する版 (0.4.0 以降) の数を出し、1 本ずつ、住所・向き・
名乗り (`/oag-node:0.4.1/` など)・繋いだときの高さ・配れるもの・繋がって
からの時間を並べる。

- **住所は上位 2 区切りだけ出す。** IPv4 は `203.168.*.*`、IPv6 は
  `2001:db8:*`。ポートは出さない。公開の頁であり、繋いでくれている人の
  家の回線をそのまま晒さない
- 名乗りは相手が好きに決める文字列である。逃がしてから埋め、版を読めない
  名乗りは数えない

#### 履歴を古い順に出すこと

アドレスの履歴は古い順に出す。索引の鍵が高さ順に並んでいるため、その順に
読むのが最も安く、続きから読むだけで頁送りになるからである。新しい順に
並べるには全件を数える必要があり、それを「途中で打ち切った」ことを隠した
まま行うのは危うい。

#### 一覧のために本体を復号しないこと

先頭の「最近のブロック」が要るのは、1 行あたり高さ・時刻・取引数・
大きさ・難易度・ハッシュだけである。時刻と難易度はブロックインデックスの
ヘッダにあり、大きさは保存した記録の長さそのもの、取引数はヘッダ直後の
varint 1 個である。**どれもブロック本体を組み立てずに取れる。**

本体を復号すると、表に出さない取引まで全部確保することになる。満杯の
ブロック ([§10](#10-コンセンサスルール)、200,000 バイト) は約 670 取引を
持ちうるので、25 行を描くために 16,000 件あまりを確保して即座に捨てる。しかもその作業は
ノード本体の処理列の中で起きるため、**その間このノードはブロックもピアも
捌いていない**。

あわせて、この一覧は**ひとつの読み取りトランザクション**で作る。高さごとに
引き直すと断面が行ごとに変わり、描いている最中に届いたブロックによって上の
行と下の行が違う時点を映す。

#### 長い一覧を区切ること

ブロック内の取引も、アドレスの履歴と同じ幅で頁に区切る。満杯のブロックを
1 枚に吐くと 670 行になる。番号は**ブロック内の通し番号**を出す。頁の中で
数え直すと、索引が指す位置 ([§19](#決着した項目)) と食い違う。

頁送りの行き先は高さではなくブロックハッシュで指す。高さで繋ぐと、サイド
チェーンのブロックを見ているときに、続きがアクティブチェーンの同じ高さの
**別のブロック**へ飛ぶ。

## 16. ウォレット

### 16.1 ノードとの関係

ウォレットはノードと **JSON-RPC でしか話さない**。チェーンの状態を持たず、
**秘密鍵はノードに渡らない**。署名はウォレット側で済ませ、出来上がった
ものだけを `sendrawtransaction` で投げる。

### 16.2 鍵の保管

**種 1 つを、パスフレーズで暗号化して保管する。**

| 手立て | 何から守るか |
| --- | --- |
| Argon2id (m=128 MiB, t=4, p=1) | 総当たり。専用機を用いても割に合わなくする |
| ChaCha20-Poly1305 | 中身を読まれること。改竄も検知する |
| ファイルの権限 0600 | 同じ機械の他の利用者 |
| 落ちるときに中身を消す | メモリやスワップに残ること |

ソルトと nonce は**保存のたびに作り直す**。同じ鍵と nonce で 2 度暗号化
すると鍵流が再利用され、平文の差分が漏れる。

#### 反復ではなくメモリを先に上げること

所要時間を同じだけ増やすなら、`t_cost` を倍にするより `m_cost` を倍に
する方が強い。Argon2 が攻撃側に強いるのは**並列に用意しなければならない
メモリの量**であり、反復回数を増やしても並べられる本数は減らないからで
ある。Argon2 自身の推奨も「まずメモリ、次に反復」である。

`m_cost` の上限を決めているのはブラウザである (§16.9)。同じ記録を携帯で
開けなければ意味がないので、携帯の wasm が確保できる範囲に収める。

#### 導出のパラメータは記録と一緒に保存すること MUST

復号は**そのとき書かれていた値**で導出する。現在の既定値で導出すると、
既定値を変えた瞬間に古い記録が開かなくなる。**開かない記録は失われた資金
と区別がつかない。**

このため既定値は後から上げてよい。上げても古い記録は開き続ける。

暗号文の外に置く項目 (ネットワーク、アドレスの数) は**認証付きデータに
含める**。含めないと、書き換えられても復号が通ってしまう。アドレスの数を
減らされれば、持っているはずのアドレスが出てこなくなる。

ファイルは**別名で書き切ってから名前を付け替える**。上書きは「切り詰めて
から書く」であり、切り詰めた直後に電源が落ちると中身が空のウォレットが
残る。**種を失えば資金は取り戻せない。**

読み込み時に権限を確かめ、所有者以外が読める場合は開くことを断る。
パスフレーズ違いと改竄は**区別せずに断る**。区別できると、改竄したものを
投げ込んで反応を見る手掛かりになる。

#### 何から守れないか

- **パスフレーズが弱ければ守れない。** Argon2id は総当たりの費用を上げる
  だけであり、当てられる程度の合言葉を強くはしない。8 文字未満は断る
- 動作中のプロセスのメモリを読める相手からは守れない。復号した種は
  使っている間そこにある
- 秘密鍵の消去は「安全な消去」ではない。最適化で省かれることも、途中で
  できた複製が残ることもありうる

### 16.3 種と鍵の導出

控えは **BIP39 の 12 語**である。そこから BIP39 の 64 バイトの種を作り、
BIP32 で BIP44 の経路をたどる ([§6.6](#66-hd-ウォレット))。

```
控えの語 (12)
    │  PBKDF2-HMAC-SHA512, 2048 回, salt = "mnemonic" ‖ 追加パスフレーズ
    ▼
種 (64 バイト)
    │  BIP32
    ▼
m / 44' / <coin_type>' / 0' / 0 / <index>
```

#### 控えは 1 つで足りる

鍵を 1 個ずつ作って並べる方式では、**アドレスを増やすたびに控えが古く
なる**。増やしたあとに古い控えから復元すると、新しいアドレスの資金が
見えない。種から導けば、あとから何個増やしても同じ控えで復元できる。

#### 保存する中身

ウォレットファイルの暗号文には、種だけでなく**エントロピーも収める**。
種だけでは控えの語に戻せない。BIP39 の種は PBKDF2 の出力であり、
一方向である。控えを表示し直せるようにするために両方を持つ。

#### 移行経路は用意しない

版数 1 (鍵を平文で並べたもの) と版数 2 (独自導出の 32 バイトの種) の
ウォレットは**読まない**。自動変換の仕組みは「古い控え」と「新しい控え」が
併存する期間を長く残すため設けない。移行前のウォレットは、秘密鍵を
書き出して新しいウォレットへ送金し直す。テストネット公開前であり、
守るべき資金が存在しない間に済ませる。

### 16.4 パスフレーズの受け取り方

**コマンドラインの引数からは受け取らない。** 引数はプロセス一覧から
同じ機械の他の利用者に見えるうえ、シェルの履歴にも残る。

端末があれば伏せ字で尋ね、なければ標準入力から読む。ファイルからも
読める (`--passphrase-file`)。

### 16.5 手数料の決め方

手数料は大きさに比例し、大きさは入力の数で決まり、入力の数は必要な額
(送る額 + 手数料) で決まる。**堂々巡りになる。**

そこで入力を 1 個ずつ増やしながら**実際に組み立てて測る**。見積もりでは
なく実物の大きさを使うため、料率を下回ることがない。BIP340 の署名は
64 バイト固定であり、署名を入れても大きさが変わらないため、署名前に
正確に測れる ([§5](#5-暗号プリミティブ))。

おつりの額はまだ決まっていないが、金額の符号化長は額によって変わる
([§7](#7-トランザクション))。取りうる最大の額を仮に置いて測る。実際の
おつりで縮むことはあってもはみ出すことはなく、差は数バイト分にとどまる。

### 16.6 ウォレットが断ること

| 断る場面 | 理由 |
| --- | --- |
| 未知の版数のアドレスへの送金 | 誰でも使える扱いになる ([§10.4](#104-未知の版数の扱い))。有効化前に送れば資金を失う |
| ダスト閾値を下回る送金 | 中継されない |
| おつりがダストになる組み立て | ダストは永久に UTXO セットに残り、誰も回収しない。手数料へ回す |
| 鍵の無い入力への署名 | 一部だけ署名して送ると、資金を動かせないまま手数料を失う (集めて回るなら [§16.8](#168-部分署名トランザクション-pst) を使う) |
| 走査が打ち切られた状態での残高表示 | 実際より少なく見せることになる |
| 8 文字未満のパスフレーズ | 暗号化しているのに守られていない状態になる |
| 既存のウォレットへの上書き | そこにあった種で守られていた資金を永久に失う |
| 版数 1 (鍵を平文で並べたもの) の読み込み | 平文のまま使い続けられてしまう |
| まとめる相手が 1 件以下でのまとめ | 手数料を払って同じ形に組み直すだけになる |

### 16.7 UTXO をまとめる

掘っていると **1 ブロックにつき 1 つ UTXO が増える**。コインベースの出力は
1 つだからである。放っておくと `scanutxos` の上限
([§15.3](#153-手続き)、10,000 件) に当たり、そこでウォレットは残高の表示も
送金も断る。走査が打ち切られた状態の残高は実際より少なく、それを見せる方が
黙って間違えるより悪いためである ([§16.6](#166-ウォレットが断ること))。

60 秒間隔なら **10,000 ブロックは約 7 日**である。掘り続ける運用では必ず来る。

#### 支払いと別の組み立てであること

支払いは「いくら送るか」が先にあり、それを賄う UTXO を選ぶ。まとめは逆で、
**UTXO を先に決めて、集めた全部から手数料を引いたものが出来高**になる。
出力は 1 つだけで、おつりは作らない。額を指定しないので、額 0 の支払いと
いう存在しない形を作らずに済む。

#### 1 回では畳み切れないこと

`MAX_TX_SIZE` ([§10](#10-コンセンサスルール)、100,000 バイト) はコンセンサス
側の上限である。入力 1 個がおよそ 102 バイトなので、**1 本に入るのは 980 件
前後**にとどまる。それを超える分は次の回に回す。何件が入り切らなかったかは、
成熟待ちの件数と**分けて**報せる。前者は確定後にもう一度実行すれば片付き、
後者は待つしかないので、混ぜると利用者はどちらを待てばよいか分からない。

小さいものから取る。どれを残しても合計は変わらないが、小さい出力ほど自分の
大きさに比べて手数料が高いので、先に畳むほど得である。

#### 上限に当たっていても、まとめは断らないこと

残高は全部を見ないと出せない。足し損ねた分だけ小さく出るので、打ち切られた
走査から残高を名乗るのは嘘である。だから残高は断る
([§16.6](#166-ウォレットが断ること))。

**まとめは違う。** 畳むのに全部は要らない。手持ちのうち何件かが返って
くれば、それを 1 つにできる。むしろ上限に当たっている状態こそまとめが要る
場面であり、そこで断ると**抜け出す道具が、抜け出すべき状態でだけ使えない**
ことになる。

返る顔ぶれは「直近の N 件」ではない。UTXO の鍵は `txid ++ 出力番号` で、
txid はハッシュだから並びは事実上でたらめである。**手持ちから適当に N 件**
であり、畳む相手としてはそれで足りる。1 回ごとに手持ちは (畳んだ件数 − 1)
だけ減るので、繰り返せば上限を下回る。

打ち切られているときは「全部畳んだ」と言わない。見えていない手持ちがまだ
ある。

#### 未確定の取引が使っている出力を手持ちに数えないこと

`scanutxos` は UTXO セットを見るので、**送信済みで未確定の取引が使っている
出力も「まだある」と答える**。そのまま組むと 1 つ前のまとめと同じ出力を使う
取引ができ、置き換えの申し出として扱われて断られる。金は減らないが、二度
実行した理由が読み取れない。mempool の取引が使っている出力を先に外す。

### 16.8 部分署名トランザクション (PST)

Bitcoin の PSBT (BIP174) 相当である。署名の済んでいない取引を、**署名に
必要なものを全部添えて**持ち運ぶための形式。

#### なぜ生の取引では足りないのか

署名の対象 (sighash) は、その取引が使うすべての出力の**金額と支払い条件**を
含む ([§8.2](#82-全入力金額へのコミット))。生の取引が持っているのは参照
(`OutPoint`) だけで、金額も条件も入っていない。したがって署名する側は
チェーンを見に行かねばならず、鍵だけを持った機械では署名できない。

#### 形式

```
PST {
    magic        [6]  = "oagpst"
    version      u8   = 1
    unsigned_tx  Transaction    // 入力の signature はすべて空 MUST
    input_count  varint         // unsigned_tx.inputs と一致 MUST
    inputs       PstInput[]
    output_count varint         // unsigned_tx.outputs と一致 MUST
    outputs      PstOutput[]
}

PstInput {
    utxo        TxOutput        // この入力が使う出力。金額と支払い条件
    sighash     u8              // Sighash の種類
    signature   var_bytes       // 長さ 0 なら未署名
    derivation  Option<Derivation>
}

PstOutput {
    derivation  Option<Derivation>   // おつりが自分のものかを確かめるため
}

Derivation { account: varint, change: varint, index: varint }
```

`Derivation` は `m/44'/<coin_type>'/<account>'/<change>/<index>` のうち
ウォレットが決める後ろ 3 つである ([§6.6](#66-hd-ウォレット))。
`purpose` と `coin_type` は仕様で決まっており、運ぶ意味がない。

**`derivation` は目安であって証拠ではない。** 署名する側は、この経路で
導いた鍵が本当にその支払い条件に合うかを必ず確かめる MUST。

#### 役割

BIP174 と同じ分け方である。

| 役割 | すること |
| --- | --- |
| 作る | 未署名の取引を組み、使う出力を添える |
| 署名する | **署名できる入力だけ**に署名を入れる |
| 束ねる | 別々に署名されたものを 1 つにする |
| 仕上げる | 全部揃っていれば取引を取り出す |

#### 守ること

- **復号のとき、`unsigned_tx` に署名が入っていたら拒否する MUST。**
  入っていると、見せている取引と署名の対象がずれる
- **束ねるとき、`unsigned_tx` が同じであることと、添えられた出力が
  一致することの両方を確かめる MUST。** 添えた出力は取引の中身ではない
  ので、txid が同じでも食い違いうる。金額が違えば sighash も違う
- **仕上げるとき、すべての署名を検証してから返す MUST。** 束ねる側が
  壊れていることも、悪意があることもある。ここで捕まえなければ、
  送ってから初めて分かる
- **すでに入っている署名を上書きしない MUST。** 他人の持ち分である
- **署名する前に手数料を見せる SHOULD**

#### `unsigned_tx` の txid は最終的な txid ではない

本チェーンの txid は取引の符号化全体のハッシュであり、**署名を含む**
([§5.3](#53-署名-schnorr-bip340))。署名が入れば txid は変わる。PST が
持っている `unsigned_tx` の txid は「同じ取引か」を確かめるための照合用で
あって、送金先に伝える番号ではない。

BIP340 のノンス生成は補助乱数を混ぜるので、同じ鍵で同じ対象に署名しても
毎回違うバイト列になる。**最終的な txid が決まるのは仕上げたあとである。**
第三者が書き換えられないことは変わらない。

#### 金額を偽る攻撃が成立しないこと

PSBT には「入力の金額を偽って渡し、署名する側に法外な手数料を払わせる」
という筋の攻撃がある。**本チェーンでは成立しない。** sighash が全入力の
金額を含むため ([§8.2](#82-全入力金額へのコミット))、偽った金額で作った
署名は本当の金額に対しては通らない。損をするのではなく、単に無効な取引が
できる。

これは §8.2 を置いた理由のひとつである。

### 16.9 ブラウザのウォレット

ノードは `--wallet` で、ブラウザに配るウォレットの口を開ける。既定は
`127.0.0.1:25565` である。

#### 鍵はノードを通らないこと MUST

**署名はブラウザの中で終わる。** 種も秘密鍵も、ノードへ送ってはならない。
口が受け取るのは署名の済んだトランザクションだけである。

ノードが差し出すのは 4 つに限る。

| 口 | できること |
| --- | --- |
| `/api/info` | 高さとネットワークを見る |
| `/api/scan` | 渡されたアドレスの未使用出力を数える |
| `/api/history` | 渡されたアドレスの履歴を読む |
| `/api/send` | 署名済みのものを mempool へ渡す |

どれも **P2P で既に誰にでもできること**である。放送する権利は元から全員に
あり、鎖の中身は公開情報である。ここを開けてもノードにできることは増え
ない。**鍵に触る口も、設定を変える口も、足してはならない MUST。**

索引が要るのは `/api/history` だけで、残りの 3 つは UTXO セットで足りる。
索引を作れない剪定ノードでは、ウォレットは履歴なしで動き、そのことを
`/api/info` が告げる。種から復元したときは未使用出力だけで使用済みの
アドレスを探すので、使い切ったアドレスは見つからない。持っているコインは
見つかる (その手前に使い切ったアドレスが 200 個続いた場合を除く)。

#### 実装を二重にしないこと MUST

ブラウザ側は `oag-wallet` を wasm に組んだものを読む。鍵の導出も、記録の
暗号化も、sighash の計算も、**CLI と同じ原稿**が動く。

暗号に関わる部分を JavaScript で書き直してはならない。実装が 2 つあれば、
いつか食い違う。食い違った先に在るのは、署名できない資金である。

記録の形式も同じなので、CLI で作ったウォレットをブラウザで開けるし、
その逆もできる。

#### 外から何も引き込まないこと MUST

配る wasm は**取り込み (import) を持たない**。ブラウザ側は
`WebAssembly.instantiate(bytes, {})` だけで動かす。

これは `wasm-bindgen` のような外部の道具に頼らないためである。道具の版数が
crate の版数と一致していなければ組めない、という状態は、**誰も作り直せない
ものを配ることに繋がる**。`cargo build` だけで作り直せることを保つ。

乱数だけは wasm 側に源が無い。`crypto.getRandomValues` が出した 32 バイトを
起動時に渡し、以後はそれを鍵にした BLAKE3 の XOF から取り出す。
**種が入る前に記録を作ってはならない MUST。** ソルトと nonce が予測できる
ものになる。

頁も JS も wasm も、この口が配ったものだけで完結させる。`Content-Security-
Policy` で読み込み元を自分自身に限る。

#### エクスプローラと同じ口にしないこと MUST

ブラウザの保存領域は `scheme + host + port` ごとに仕切られる。**別の口に
すれば仕切りも別になる。** エクスプローラ側に差し込みの穴があっても、
暗号化された記録はそちらから読めない。

同じ口に相乗りさせると、この仕切りが消える。エクスプローラは取引 ID や
アドレスを頁に埋めており、そこに穴が無いことを永久に保証はできない。

#### 平文で外に配らないこと MUST

通信路が平文でも、**署名が中身を守る**。宛先も金額も署名が及んでいるので、
途中で書き換えられない。握り潰せるだけである。

守れないのは**頁を配る線**である。署名するコードは毎回ブラウザへ送られる。
そこを差し替えられれば、見た目は同じまま種を持ち出せる。

したがって、ループバック以外で待ち受けるには証明書を渡すこと。渡されて
いなければ**起動を断る**。手元で試すだけなら平文でよい。

#### 送り元を選んだら、お釣りもそこへ戻すこと MUST

送金の画面では、送り元を「どのアドレスからでも」か、1 つのアドレスに
絞るかを選べる。絞ったときは**そのアドレスの出力だけを使い、お釣りも
そのアドレスへ戻す**。既定のアドレス (番号 0) へ戻すと、分けて使って
いたアドレスが混ざり、絞った意味がなくなる。

お釣りの宛先は、**この財布が鍵を持つアドレスに限る MUST**。持たない
アドレスが渡されたら組み立てを断る。打ち間違い一つで、お釣りが他人の
ものになるからである。

絞らないときは従来どおり、どの出力も使い、お釣りは既定のアドレスへ
戻す。

#### 置き場は控えではないこと

暗号化した記録は localStorage に置く。ただしこれは**キャッシュであって
控えではない**。origin が変われば消え、しばらく開かなければ消える処理系も
ある。

したがって、作った直後に**控えの語を書き留めさせるまで先へ進ませない**。
記録が消えても、語があれば戻せる。

#### 語から戻すときに未使用出力だけを見ないこと MUST

控えの語には「何個まで配ったか」が書かれていない。探すには、まだ自分の
ものと決めていない番号のアドレスを先に導いて、鎖に問い合わせる。

このとき**未使用出力だけを見てはならない**。受け取って全部使ったアドレスは
未使用出力を持たないので、そこで探索を止めると、その先の資金を見落とす。
**使われた形跡は履歴で見る** (§15 の索引が要る)。

経路は `m/44'/1033'/0'/0/<index>` の一本道であり、口座もお釣りの枝も
分かれない (§16.3)。走査するのは番号だけである。番号が変わりうる間は
(§16.3 の SLIP-0044 の項)、**経路を配列で持つ**こと。`/api/scan` は
アドレスの配列を取るので、新旧 2 本分を同じ 1 回に混ぜられる。

## 17. 相互運用性と DEX

### 17.1 前提

本チェーンは以下の 2 つの性質を持つ。

1. **資産が OAG の 1 種類のみである。** トークン発行機能を持たない。
2. **スクリプト言語を持たない。** 条件付き支払いを直接表現できない。

したがって:

| 種類 | 可否 |
| --- | :---: |
| クロスチェーン アトミックスワップ (OAG ↔ BTC / LTC / XMR 等) | **可能** |
| P2P スワップ市場 (板はオフチェーン、決済はスワップ) | **可能** |
| 他チェーンへブリッジして既存 DEX で取引 | **可能** (要ブリッジ運営) |
| 同一チェーン内の板取引 DEX | **不可** (交換相手の資産が存在しない) |
| AMM 型 DEX (Uniswap 等) | **不可** (実行環境がない) |
| レンディング / デリバティブ | **不可** (同上) |

### 17.2 アダプター署名によるアトミックスワップ

Schnorr 署名の線形性により、**スクリプトを一切用いずに**
クロスチェーンのアトミックスワップが構成できる。

```
1. 両者が MuSig2 で 2-of-2 の集約鍵を作り、そこへ資金を送る
   → チェーン上は通常の単一署名の送金と区別がつかない

2. 資金を送る前に、locktime 付きの返金トランザクションを相互に事前署名する
   → 相手が離脱しても時間経過後に取り戻せる

3. 一方のチェーンで署名が公開されると、アダプター署名の性質により
   その署名から秘密値が復元でき、他方のチェーンの資金が解錠される
```

**HTLC 方式に対する優位性**:

- スクリプトを必要としない (本チェーンで実現可能な唯一の方式)
- 両チェーンに同一のハッシュ値が刻まれないため、
  2 つの取引が関連していることが外部から判別できない
- 通常の送金と同じサイズ・同じ形式

**成立に必要なプロトコル要件** (すべて本仕様に含まれている):

| 要件 | 該当箇所 |
| --- | --- |
| BIP340 Schnorr 署名 | [5.3](#53-署名-schnorr-bip340) |
| トランザクション ID の非展性 | [5.3](#53-署名-schnorr-bip340) |
| 絶対 locktime | [7.4](#74-locktime) |
| 相対 locktime の意味論 | [7.5](#75-sequence-相対-locktime) |
| Sighash フラグ | [8.3](#83-sighash-フラグ) |

MuSig2 とアダプター署名は**完全にウォレット層の技術**であり、
コンセンサスの変更を一切必要としない。したがって v1 では実装せず、
後からウォレット側の機能追加として提供できる。

### 17.3 将来の拡張余地

より高度な取引機能が必要になった場合の拡張経路を、
アドレス版数の予約領域として確保してある ([6.3](#63-アドレス版数))。

```
version 1 →  スクリプトハッシュ等 (予約)
version 2 →  予約
version 3 →  コミットメント出力 (0.5.0、§7.7)
```

HTLC 型の出力は、条件 (ハッシュ 32 + 鍵 2 つ 64 + 期限 8 バイト) が出力の
中身の上限 (40 バイト) にも、入力の署名欄の上限 (100 バイト) にも収まらない
ため、今の形のままでは入らない。入れるなら、SegWit (BIP141/144) のように
データを txid の外に置く仕組みを先に作ることになる。スワップは当面
[§17.2](#172-アダプター署名によるアトミックスワップ) の方式で足りる。

これらはソフトフォークとして追加できる。旧ノードは未知の version の出力を
**コンセンサス上は誰でも使用可能 (anyone-can-spend) として扱う**ため、新ノードが
その版数に条件を課しても、新ノードの作るブロックは旧ノードにとって有効なままで
ある ([§10.4](#104-未知の版数の扱い))。有効化までの間その版数へ送金してはならず、
旧ノードが標準外として中継しないのはその危険を減らすためのポリシーであって、
コンセンサスルールではない。

**AMM を実現するには任意計算の実行環境が必要であり、
それは本仕様の範囲を超える別の設計となる。**

## 18. 設計判断の記録

主要な選択と、その理由を記録する。

| 判断 | 選択 | 理由 |
| --- | --- | --- |
| 合意形成 | PoW (RandomX) | CPU 採掘による公平な分配。ASIC 耐性 |
| 実装言語 | Rust | GC がなくブロック検証のレイテンシが決定的。型システムがコンセンサス状態機械に適する。RandomX の FFI が cgo より軽い。Tari という先例 |
| 会計モデル | UTXO | 検証が単純。並列検証が容易 |
| 署名曲線 | secp256k1 | libsecp256k1 の実績。ハードウェアウォレット対応。BIP32 の非強化導出が使える |
| 署名方式 | Schnorr (BIP340) | 展性がない。64 バイト固定。バッチ検証。MuSig2 とアダプター署名が使える |
| 汎用ハッシュ | BLAKE3 | 高速。Rust が参照実装。長さ拡張耐性があり二重ハッシュ不要 |
| 金額型 | u128 | 10^25 atomic は u64 に収まらない |
| 小数桁数 | 16 | — |
| 発行カーブ | 線形・半減期なし | 実装が単純でオフバイワンの余地がない。半減期に伴うハッシュレートの断崖がない。長期にわたり新規参加者に採掘機会が残る |
| 初期配布 | なし | 公平な分配という設計目標の中核 |
| タイムスタンプ | i64 | 発行完了が 2216 年であり u32 は 2106 年に破綻する |
| 難易度表現 | u64 直接 | nBits の非正準符号化に起因するバグ類を回避。LWMA が難易度を直接扱う |
| マークルツリー | RFC 6962 | Bitcoin の CVE-2012-2459 を構造的に回避 |
| アドレス | bech32m | 4 文字以内の誤りを 100 % 検出。大文字小文字の混在を禁止。QR が小さい |
| 手数料 | バイト単価 / ノードポリシー | スクリプトがないためガス (計算量課金) は不要。価格変動にハードフォークなしで追随できる |
| プライバシー | なし | 実装量と監査費を大幅に削減。取引サイズが Monero の約 1/8 |
| P2P | 独自実装 | 要件が単純。libp2p の依存の重さが利益を上回る |
| ストレージ | redb | 純 Rust でクロスコンパイルが容易 |
| ブロックインデックスの常駐量 | 実体は記憶域に置き、常駐は先端の候補と上限つきの控えだけにする | 全件を抱えると 1 件 500 バイト × 年 52 万ブロックで、10 年 2.5 GB、20 年 5 GB になる。ディスクでも初期同期でもなく常駐量が先に限界へ届く。Bitcoin が全件を置けるのは 10 分間隔だからであり、60 秒間隔では保たない ([§19](#決着した項目)) |
| チェーン選択の候補 | 作業量順の集合を漸進的に保つ | 全件走査は 1 ブロックあたり O(n)、初期同期全体で O(n²) になる。10 万ブロックで記憶域への書き込みに匹敵する ([§10.6](#106-最長チェーンの選択)) |
| ニーモニック | BIP39 12 語 (128 ビット) | 128 ビットは secp256k1 の実強度 2^128 と一致する。種を長くしても曲線より強くならず、書き写しの誤りが増えるだけである ([§6.6](#66-hd-ウォレット)) |
| 鍵導出 | BIP32 / BIP44 | 標準の語彙で書いた控えを他のウォレットが別の鍵に解釈する状態を作らない。ハードウェアウォレットへの道も残る |
| mainnet のコインタイプ | 申請した番号 1033 を実装に入れる。公開は登録の完了まで待つつもりだったが、待たずに公開した | 経路を先に固定しておけばウォレットの検証が進む。別の番号で受理されたら、1033 の経路も読めるように残したまま移す ([§6.6](#66-hd-ウォレット)) |
| ソフトフォークの有効化 (0.5.0 から) | 採掘者の印 (BIP9 の形、高さで区切る)。1,440 ブロックごとに 2/3、猶予 1 区切り、約 1 年で失敗 | 人が増えて、採掘者全員に直接連絡がつく前提が崩れた。高さを決め打ちにすると、更新していない採掘者がいるまま強制が始まりうる ([§10.9](#109-ソフトフォークの有効化-採掘者の印)) |
| コミットメント出力 | 版数 3、金額 0、中身 2〜40 バイト、UTXO に入れない | ハッシュを刻む用途は多いが、スクリプトの置き場は作らない。UTXO に入れなければ全ノードの常駐量を汚さない (Bitcoin の `OP_RETURN` と同じ) ([§7.7](#77-コミットメント出力)) |
| 軽い枝のヘッダ | 最良のヘッダより 144 ブロック分以上軽い枝は書かずに手元に置く | 難易度の低い昔の高さから分岐させれば、正しいヘッダを安く大量に作れる。リオーグの深さには上限を設けずに、ディスクを守る (Bitcoin Core と同じ) ([§10.5](#105-検証順序-dos-対策)) |
| 相対 locktime | 高さを決めたソフトフォークで強制を始める。対象は版数 2 以上 | 意味論は v1 で確定済みであり、強制を入れるだけで済む。版数 1 は `sequence` に意味が無かった時期の取引なので対象から外す (BIP68 と同じ)。合図 (version bits) を使わないのは、採掘者が少なく直接連絡がつくからである ([§7.5](#75-sequence-相対-locktime)) |
| 未知の出力版数 | anyone-can-spend を維持し、版数を 0〜31 に制限 | 拒否すると版数追加が必ずハードフォークになる。範囲の制限はソフトフォークの余地を減らさずに危険面積を減らす ([§10.4](#104-未知の版数の扱い)) |
| マージマイニング | v1 では無効 | 単体チェーンのデバッグと Monero 連携のデバッグを同時に走らせない。ヘッダに拡張枠のみ確保 |
| 部分署名取引 | PSBT (BIP174) と同じ役割分担。使う出力を添えて運ぶ | sighash が全入力の金額と支払い条件を含むため、生の取引だけでは鍵を持つ機械が署名できない ([§16.8](#168-部分署名トランザクション-pst)) |
| 住所帳 | `addrman` と同じ二表構造。`new` から `tried` への昇格に接続の成功を要求する | 1 つの表では、多数の /16 を持つ相手に埋め尽くされる。二表にすると、外向きの接続の半分が実績のある相手に向かうことを構造で保証できる ([§14.6](#146-ピア発見)) |
| 手数料を上げた置き換え | BIP125 の規則 2〜5 を適用し、規則 1 (置き換え可能の表明) は求めない | 表明は守れない約束である。採掘者は手数料の高いほうを選べばよく、表明を見ないノードが 1 つ中継すれば置き換えは伝わる。「表明していないから 0 承認で安全」を掲げると、信じた受け取り側が損をする ([§13.3.2](#1332-手数料を上げた置き換え-rbf)) |
| 受け取り側の確認数 | 目安を 10 ブロックとし、コンセンサスルールにはしない | 覆る確率は q と承認数だけで決まりブロック間隔に依らないので、6 でも Bitcoin と同じ確率になる。違うのは費用で、若いチェーンは全体のハッシュレートが小さいぶん同じ占有率が安く買える。その差を承認数で埋めて 10 とした。ノードに強制させないのは、何を待つかが受け取り側の損得の問題であり、合意の問題ではないからである ([§10.7](#107-受け取り側の確認数)) |
| リオーグ後の mempool | 取り消された枝のものを戻したうえで、**mempool 全体を検証し直す** | 落ちたものを選んで外すやり方では、親を失ったもの、高さが戻って成熟や locktime に届かなくなったものを取りこぼす。崩れたまま残すと、それを詰めた自分のブロックが自分で弾かれる。リオーグは稀で mempool には上限があるので、選別の複雑さより全件の検証を取った ([§10.6](#106-最長チェーンの選択)) |
| 負けた枝のブロック | mempool を触らない | そのブロックはアクティブチェーンに無く、入っているトランザクションは依然未確認である。外すと、まだ有効な支払いを中継も採掘もしなくなる。分岐は普通に起こるので影響が小さくない ([§10.6](#106-最長チェーンの選択)) |

### 検討したが採用しなかったもの

| 案 | 不採用の理由 |
| --- | --- |
| Cosmos SDK / 独自 PoS チェーン | RandomX (PoW) と両立しない |
| ERC-20 トークンとして発行 | 独自チェーンを持つという目標に反する |
| Go 言語 | RandomX が cgo 経由となり、呼び出しコストとクロスコンパイルの負担が Go の開発速度の利点を相殺する |
| ECDSA | 展性がある。バッチ検証ができない。MuSig2 が使えない |
| Ed25519 | BIP32 の非強化導出が使えず xpub 運用ができない。ハードウェアウォレット対応が重い |
| 半減期方式 | 総発行 10 億・報酬 10 OAG と両立させるには半減期が 95 年となり機能しない |
| プライバシー機能 (RingCT 等) | 実装量と監査費が過大。取引サイズが 8〜12 倍になる |
| 1 MB ブロック | 年間 526 GB の成長となりノード運用が不可能になる |
| SegWit 相当の機構 | Schnorr + スクリプトなしの構成では展性が存在せず不要 (65 バイトで末尾 `0x00` の署名という例外は、0.5.0 のソフトフォークで塞いだ。[§5.3](#53-署名-schnorr-bip340)) |
| HTLC 型の出力 (0.5.0 の時点) | 条件が出力 (40 バイト) にも署名欄 (100 バイト) にも収まらない。入れるには SegWit 相当の仕組みが先に要る。スワップは [§17.2](#172-アダプター署名によるアトミックスワップ) で足りる |
| チェックポイント (固定のブロックハッシュ) | 十分に深く埋まり、複数の独立したノードで確かめたハッシュがまだ無い ([§10.8](#108-assumevalid-初期同期の短縮) と同じ基準)。軽い枝の対策は作業量の閾値で足りる |
| 24 語のニーモニック | 256 ビットの種を用いても、導かれる鍵の強度は secp256k1 の 2^128 で頭打ちになる。控えが倍の長さになる分だけ書き損じが増える |
| 未知の版数を無効とする | 版数の追加が必ずハードフォークになる。全ノードの同時更新を要求するほうが、3 層で緩和済みの資金喪失より危険である |
| 登録が済む前に mainnet を公開する | 別の番号で受理された時点で、既存の控えから導かれる鍵が変わる。利用者から見れば資金が消えたのと区別がつかない |
| 独自の語彙によるニーモニック | BIP39 の語彙は 4 文字の接頭辞で一意に定まり、既存の実装と辞書がそのまま使える |
| トランザクション索引を既定で持つ | 満杯時に年間 37 GB の上乗せをすべてのノードが払うことになる。コンセンサスは UTXO セットしか要求せず、ウォレットは自分に関係する取引だけを記録すれば足りる。必要になった運用者が `--index` で有効にする |
| 最大リオーグ深度を設ける | 蓋より深く分かれたネットワークが二度と合流しなくなる。攻撃の可能性を残すほうが、恒久的な分裂を作るよりよい |
| コインベース成熟を延ばす | リオーグを押し返すのに要るのは時間ではなく累積作業量であり、ブロック数では既に Bitcoin の 100 より深い 120 である。延ばして変わるのは報酬を受け取れるまでの待ち時間だけで、リオーグの費用は変わらない |
| 「この高さまで使えない鍵」の出力版数 (CLTV 相当) | 他人の資金を凍結する攻撃には使えないが、ロック中の出力で支払ったように見せる偽装、有効化前の版数の横取り、時刻で解禁する場合のタイムスタンプ操作といった扱いを要する点が増える。相対 locktime と事前署名で足りる用途が多い |
| SIGHASH_ANYPREVOUT (BIP118) | eltoo を安全に動かすには、古い状態が新しい状態を上書きできないよう順序を強制する必要があり、それには CLTV 相当の検査が要る。また、既知の鍵と組み合わせると出力の使い道を縛る仕組み (covenant) が作れ、スクリプトを持たないという方針とぶつかる |
| 置き換えに料率の上昇も求める | BIP125 の規則 3・4 は総額しか見ず、大きくて料率の低いものが小さくて料率の高いものを追い出せる。ここで独自の規則を足すと mempool の中身がノードごとにばらけ、Compact Blocks の当たり外れに直結する。弱点を承知で互換を優先する |

#### ブロックインデックスの常駐量は高さに比例させない

**知っているブロックの実体をメモリに常駐させない MUST NOT。**

ブロック間隔が 60 秒であるため、同じ年数で Bitcoin の 10 倍積まれる。
1 件あたり 500 バイト前後で全件を抱えると、10 年で 2.5 GB、20 年で 5 GB、
発行が完了する 190 年後には 50 GB になる。**先に限界へ届くのはディスク
でも初期同期でもなく、常駐量である。** 本体は空のブロックで 203 バイト
なので 1,000 万ブロックでもディスクは 2 GB であり、初期同期も実測
45 blk/s で 2 日半、Bitcoin の現状と同程度に収まる。

常駐するのは次の 2 つだけである。

| | 何で決まるか |
| --- | --- |
| 先端の候補 (作業量順の集合) | **競合する枝の数。** 分岐が無ければ 1 本ぶん |
| 最近引いた実体の控え | **上限。** 4096 件、約 1 MB |

どちらも鎖の長さによらない。実体の正本は記憶域にあり、控えから落ちた
ものは引き直す。親から子への写像も記憶域が持つ (無効の印を子孫へ広げる
ときにしか引かない)。

先端の候補は、先端の作業量を下回った時点で捨ててよい。切り替える相手は
厳密に上回る枝だけであり ([§10.6](#106-最長チェーンの選択))、先端の
作業量は決して減らないため、下回ったものが再び候補になることはない。

起動時に全件を同時に載せてはならない MUST NOT。先端を先に読み、1 件ずつ
受け取って、先端を下回るものはその場で捨てる。読む量は変わらないが、
同時に持つ量は一定になる。

**控えに無いことを「知らない」と扱ってはならない MUST NOT。** 引けなかった
ときは誤りとして返すこと。混同すると、正しいブロックを知らないものとして
扱い、静かにチェーンから外れる ([§11.3](#113-シードエポック) のシード
解決と同じ誤りである)。

#### 複数スレッドでの採掘はデータセットを共有する

**0.1.1 で判断を覆した。** 下の「0.1.0 の判断」は当時の記録として
残す。

##### 0.1.1 で覆した理由

「代償は memory だけ」と書いたが、その memory が大きすぎた。

- fast を 6 スレッドで掘ると **12 GB** になる。実際に 6 スレッドで掘る
  利用者がいた。Monero や XMRig なら同じ本数で 2 GB である
- データセットの構築 (1 分前後) も本数だけ走る。エポックごとに繰り返す
- 大きなページで速くしようとすると、大きなページも本数の掛け算で要る。
  12 GB 分の大きなページは、Windows ではまず取れない

そこで (b) を採った。ただし「薄い crate」は作らず、`oag-pow` の
`SharedDataset` に `unsafe impl Send / Sync` の 2 行だけを置いた。
`unsafe` の本体 (ポインタを触る処理) は書いていない。書いたのは「この型は
スレッドをまたいでよい」という宣言だけで、その根拠は型の説明に並べてある。

作り方を渡す仕組みは残した。作り方が `SharedDataset` を抱えて渡り、
VM は各作業スレッドの上で建つ。変わったのは作り方の中身だけである。

(a) も残っている。上流が `Send` / `Sync` を足せば、この 2 行は要らなく
なる。`oag-pow` の `const _` が、そのときにビルドを失敗させて知らせる。

##### 0.1.0 の判断

問いは「`RandomXDataset` が `Send` でないので 2 GB を共有できない。
どうするか」であった。選択肢は (a) `randomx-rs` に `Send` を足して
もらう、(b) データセットを扱う薄い crate だけ `unsafe` を許す、
(c) 1 スレッドで我慢する、であった。

**どれでもない。問いの立て方が狭かった。** 共有が要るのは「採掘器を
1 個建てて配る」と決めてかかった場合だけである。**配るのを採掘器から
作り方に変えれば、共有は要らない。** スレッド境界を越えるのはシードの
値だけになり、採掘器はそれぞれのスレッドの上で建って、そこから動かない。
`unsafe` は要らず、上流の変更も待たなくてよい。

代償は memory である。共有しないのだから本数だけ要る
([§11.2](#112-動作モード) の表)。light モードなら 1 本 256 MB なので、
8 本建てても 2 GB、fast 1 本と同じである。**fast 1 本と light 8 本の
どちらが速いかは機械による。** 倍率を仕様に書かない理由でもある。

(a) は残っている。上流が `Send` を足せば fast のデータセットを共有でき、
fast の多スレッドが 2 GB で済むようになる。そのときは作り方を渡す
仕組みの中だけを差し替えればよい。`oag-pow` の `const _` が、上流が
`Send` を足した瞬間にビルドを失敗させて知らせる。

#### トランザクション索引を既定では設けない

txid から取引を引く索引も、支払い条件から取引を引く索引も、**既定では
持たない**。コンセンサスが必要とする索引は UTXO セットだけであり、検証が
「この txid の取引はどこか」を問う場面は無い (入力が指すのは常に
`OutPoint` である)。

Bitcoin が `-txindex` を既定で無効にしているのと同じ判断である。ウォレット
は自分に関係する取引だけを記録すれば足りる ([§16.1](#161-ノードとの関係))。

**エクスプローラのように全件を引く必要が実際に生じたので、任意機能として
足した。** `--index` を渡したノードだけが作る。既定は変えていない。

##### 鍵を縮める

素直に作ると、txid 32 バイトと支払い条件のハッシュ 32 バイトがそのまま
鍵になる。満杯のブロックが続く場合、これは**年間 124 GB** を要する。
チェーン本体の 105 GB/年より索引のほうが重い。

そこで鍵を 14 バイトに縮める。

```text
┌──────────────┬──────────┬────────┐
│ 接頭辞 8 B   │ 高さ 4 B │ 位置 2 B│
└──────────────┴──────────┴────────┘
  ハッシュの頭   u32 BE     u16 BE
```

値は持たない。**鍵そのものが位置を表す。** これで年 124 GB が **37 GB**
になる。

| 索引 | 素直な鍵 | 縮めた鍵 |
| --- | --- | --- |
| 取引索引 (txid → 位置) | 35 GB/年 | 7 GB/年 |
| アドレス索引 (lock → 取引) | 89 GB/年 | 30 GB/年 |
| 合計 | 124 GB/年 | **37 GB/年** |

いずれも満杯のブロックが 1 年続いた場合である。満杯は 1 分あたり 673 件、
毎秒 11 件であり、Bitcoin の約 1.6 倍にあたる。実際の使われ方では桁が
いくつも下がる。

接頭辞 8 バイトは**衝突する**。しかし誤答にはならない。索引が返すのは
「ここを見ろ」という位置であって答えではなく、呼び出し側はその位置の取引を
読んで**完全な txid または完全な lock と突き合わせる**。一致しなければ
捨てる。衝突は余計な候補が 1 件増えるだけである。2^64 に 3.5 億件を入れた
ときの衝突の期待値は約 0.003 件であり、狙って作るには 2^64 の作業を要する
うえ、成功しても得られるのは照会を 1 回無駄足にすることだけである。

高さと位置をビッグエンディアンで置くのは、**バイト順をチェーン順に
一致させる**ためである。同じ接頭辞を前方一致で範囲走査すれば、履歴が
古い順に並んで出てくる。並べ替えが要らず、続きから読むだけで頁送りになる。

##### 索引は UTXO セットと同じトランザクションで動かす

索引の更新は、ブロックの接続・切断と**同じ書き込みトランザクションの中**で
行う。別に分けると「UTXO は進んだが索引は古い」状態が存在しうるようになり、
電源が落ちるたびにその食い違いを直す仕掛けが要る。同じ中に入れておけば、
索引は常に UTXO セットと同じ地点を指す。

入力側のアドレスは**巻き戻し情報から引く**。入力は `OutPoint` しか名乗らず、
指している出力は UTXO セットから既に消えている。リオーグのために取ってある
記録が、唯一の手掛かりである。

##### 途中からの索引を作らない

組み直しも 1 つのトランザクションで行う。途中で電源が落ちたときに
**半分だけの索引が残るのが最悪である**。索引は「無い」なら照会を断れるが、
「半分ある」ことを知らなければ、欠けた履歴を完全なものとして返してしまう。
利用者はそれを信じる。区別のつく状態しか作らない。

#### コインベース成熟は 120 ブロックのまま

「2 時間は短いのではないか」という問いであった。比べる単位が違う。

リオーグを押し返すのに要るのは**累積作業量**であり、それはブロック数に
比例する。時間ではない。Bitcoin の 100 ブロックに対して本チェーンは
120 ブロックであり、**ブロック数では Bitcoin より深い**。1 ブロックが
60 秒なので実時間は短く出るが、その 2 時間の間に積まれる作業量は
120 ブロック分である。

低ハッシュレート期に 120 ブロックのリオーグが絶対額として安いのは事実
である。**しかしそれは成熟期間を延ばしても直らない。** 延ばして直るのは
「報酬を受け取れるまでの待ち時間」だけで、リオーグの費用は変わらない。
効くのは難易度調整 ([§12](#12-難易度調整-lwma)) と、少ない承認数で
確定と見なさないことである。

#### 最大リオーグ深度を設けない

設ければ 51 % 攻撃で書き換えられる範囲に蓋ができる。代わりに、**蓋より
深く分かれたネットワークは二度と合流しない**。合流できないチェーンは、
攻撃されたときに「攻撃者の枝と正直な枝のどちらが本物か」を人が決める
までもとに戻らない。

本チェーンの収束は累積作業量だけで決まる ([§10.6](#106-最長チェーンの選択))。
Bitcoin も同じであり、深度の制限を持たない。攻撃の可能性を残すほうが、
恒久的な分裂の可能性を作るよりよい。

#### ただし巻き戻し情報は運用者が捨ててよい

巻き戻し情報 (undo) は**再編成で戻るときにしか読まない**。接続のたびに
1 件増え、大きさはそのブロックが使った UTXO の中身に比例する。満杯の
ブロックが続けば年間で数十 GB に達する。

実装はこれを剪定する機能を持ってよい。ただし、

- **既定では剪定しない** (SHOULD NOT)。上の決定をそのまま残す。
- 剪定は**コンセンサス規則ではない**。受け入れるブロックの集合は変わらず、
  剪定したノードと剪定していないノードは同じチェーンに収束する。
- 剪定した深さより深い再編成に出会ったとき、**黙って別の状態を作っては
  ならない** (MUST NOT)。追従できないことを告げ、運用者が引き直せる
  ようにする。

「蓋より深く分かれたネットワークは二度と合流しない」という上の懸念は、
コンセンサス規則としての蓋に当てはまる。記憶域を捨てたノードは、
**引き直せば正しいチェーンに戻れる**。恒久的な分裂にはならない。

`oag-node` は `--prune-undo <blocks>` で有効にする。値を省くと 4320
(60 秒ブロックで 3 日分)。

#### ブロック本体も同じ条件で捨ててよい

本体は**他のノードへ配るためにしか持っていない**。自分の検証に要るのは
UTXO セットであり、それは剪定しても丸ごと残る。

実装は本体を剪定する機能を持ってよい。巻き戻し情報と同じ条件に加えて、

- **剪定したノードは `SERVICE_FULL_NODE` を名乗ってはならない**
  (MUST NOT, [§14.5](#145-p2p-プロトコル))。`SERVICE_LIMITED` を名乗る。
- 持っていない本体を求められたら `notfound` を返す (MUST)。**黙って
  応じないのは最も悪い**。相手は時間切れまでそのブロックを待ち、
  ブロックは親から順にしか繋がらないので、止まるのはその 1 個では済まない。
- **ヘッダの連なりは切らさない** (MUST)。索引が持つヘッダと親子関係は
  剪定しない。切らすと、自分がどのチェーンに居るのかを創世まで辿って
  確かめられなくなる。
- **検証は変わらない** (MUST)。剪定したノードも、新しいブロックの署名・
  金額・二重使用・成熟・PoW をすべて検証する。剪定は配る能力の話であって、
  信用の話ではない。ここが軽量ノードとの分かれ目である。
- ジェネシスは残してよい。1 ブロック分の費用しかない。

剪定した記憶域では**取引索引を作れない** (MUST NOT)。捨てた本体の取引を
索引に入れる術はなく、欠けた索引を完全なものとして返せば、利用者はそれを
信じる。「完全にあるか、まったく無いか」だけを作る。

剪定したことは**記憶域の側に記録する** (MUST)。設定を外して起動し直しても
捨てたブロックは戻らない。設定だけを見て名乗りを決めると、配れないものを
配れると言うことになる。

同期の相手を選ぶとき、本体がまだ追いついていないノードは
`SERVICE_FULL_NODE` を名乗る相手を優先してよい。**ただし、名乗りを聞いた
ことのない住所を外してはならない** (MUST NOT)。名乗りは握手で初めて分かる
ので、外すと住所帳が空の状態から 1 本も繋げなくなる。

`oag-node` は `--prune <blocks>` で有効にする。値を省くと 4320。本体と
巻き戻し情報を同じ深さで刈るため `--prune-undo` とは併用できず、索引を
必要とする `--index`・`--explorer` とも併用できない。`--wallet` は索引
なしで動く (§16.9)。
受け付ける一番浅い深さは 144 で、これより浅いと日常的な 1〜2 ブロックの
入れ替わりで戻れなくなる。

#### 軽量ノードは、まずプロトコルを変えずに作る

軽量ノード (ヘッダしか持たないノード) は、**既存のメッセージだけで作れる**。

```text
getheaders / headers    ヘッダの連なり。PoW を自分で検証する
getdata(Block) / block  中身をもらう。merkle root を自分で計算し直す
```

**merkle proof は要らない。** proof が存在する理由は「ブロックを落とさずに
済ませるため」であって、検証を強くするためではない。ブロックが手元にある
なら root は自分で計算できる。フィルタも proof も**帯域を節約する道具で
あり、省いても安全性は落ちない**。

したがって `PROTOCOL_VERSION` は据え置きでよく、稼働中のノードは何も
変えなくてよい。

##### 混んできたときに作り直さないための決め事

後からフィルタ (BIP158 相当) を足せるように、軽量ノードは次の 2 つを
**別々の段として実装する** (SHOULD)。

1. **取るかどうかを決める段** — いまは「常に取る」。後にフィルタを引いて
   一致したときだけ取る、に差し替わる
2. **確かめて拾う段** — ブロックを検証し、自分の lock に触れる取引を拾う

**2 は前後で 1 ビットも変わらない。** どちらの経路でも最後に手元へ来るのは
ブロックそのものであり、確かめ方は同じだからである。フィルタは 1 の中だけ
で完結する。ここを混ぜて書くと、混んできたときに全部書き直すことになる。

##### フィルタをブロックへコミットしない

フィルタの要約をヘッダへ入れてはならない (MUST NOT)。ヘッダの書式を変える
のはハードフォークであり、**稼働中のチェーンでは払えない代償**である。
Bitcoin も BIP157/158 でコミットしないほうを選んでいる。

コミットしないフィルタは、相手が偽れる。偽られると**自分宛の支払いを
見落とす** (無い取引をでっち上げられはしない。ブロックを取れば分かる)。
複数のピアから引いて突き合わせることで補う。これは軽量ノードが元から
負っている性質であり、フィルタが新たに持ち込むものではない。

##### 名乗りはそのとき足せばよい

フィルタを配れることは `SERVICE_COMPACT_FILTERS` (`1 << 2`) として
名乗る。[§14.5](#145-p2p-プロトコル) の `effective_services` は未知の
ビットをそのまま通すので、**ビットを足すだけなら稼働中のノードに影響は
ない**。剪定ノードの `SERVICE_LIMITED` で既に通った道である。
